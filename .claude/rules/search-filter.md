# ファイル名の検索・絞り込み・外部コマンドの起動

> 機能別の設計メモ。上の `paths:` のファイルを触ると自動で読み込まれる。`Application.cc` など複数の機能が同居するファイルでは載らないので、そのときは CLAUDE.md の「設計メモの索引」から、該当するファイルを自分で読むこと。
> テスト・実測・実機未確認の記録は `.claude/notes/search-filter.md`（自動では読み込まれない。テストを書く・直す・検証するときに読む）。

## ファイル名の検索（インクリメンタル検索）

`Miata.command.search()` / `search_next()` / `search_prev()` / `search_clear()`（`Application.cc` の `lua_command_search*`）→ `View::BeginSearch` ほか → `BrowserView` → `FileListView`。vim の `/` `n` `N` のように、検索語を入れていくと一致するファイル名へカーソルが飛び、名前の一致部分が強調される。ユーザー向けの仕様は README の「ファイル名の検索」。ここには、設計の決定と罠を書く。

- **3つに分けた**：`SearchState`（AppKit 非依存。1ペイン分の状態遷移 Idle → Typing → Committed と、ヒットからの計算 `FirstHitFrom`/`Step`/`Ordinal`/`RangesFor` だけ。マッチ自体は持たない）、`FileListView`（実際のマッチ `RebuildSearchHits`（`NameMatcher` を使う。絞り込みと共用）、カーソルの移動 `JumpCursorTo`、ハイライトの描画 `Draw`。検索状態は `search_`）、`QueryBar`（pimpl。背景のビュー + `NSTextField` 3つ（プロンプト「/」・入力欄・件数）+ delegate。絞り込みと共用で、プロンプトを引数に取り、表示内容は呼び出し側が `Display` で渡す）。バーは**ペインごと・種類ごとに1つ**、`BrowserView` が持ち、入力の始まりと終わり、ペインの状態との整合を担う（絞り込みと並ぶと2段になる。後述「絞り込み（フィルタ）」）
- **マッチ**：`NSString` の `rangeOfString:options:range:`（名前は `@(Name().c_str())`）。返る `NSRange` は名前の UTF-16 の添字で、そのまま `NSAttributedString` の属性範囲に使える（UTF-8 との変換が要らない）。スマートケース：語に Unicode の大文字（`uppercaseLetterCharacterSet`）が1文字でもあれば `0`（区別する）、無ければ `NSCaseInsensitiveSearch`。**`NSLiteralSearch` は付けない**（付けると、合成済みの文字と分解された文字（NFC の `が` と `か` + 濁点）が一致しなくなる。`Name()` は NFC だが、検索語は NFD で来ることもある）。範囲の長さは**名前の側**の長さ（検索語の長さと同じとは限らない）。全角/半角・ひらがな/カタカナ・アクセントは畳み込まない（実測）。`FzfFilter` は使えない（外部プロセスを起動し、一致位置を返さず、結果がスコア順）
- **ヒットは `list_` を作り直すたびに作り直す**：`list_` を作り直すのは `ApplyFilter()` だけで（`Fetch()` の末尾と、絞り込みの語の変更から呼ばれる。ディレクトリ移動・手動/自動リロード・ソートはすべて `Fetch()` を通る）、ヒットは `list_` の添字なので、そのたびに無効になる。`Draw()` の中では計算しない。検索状態に持てるのは、検索語・位置のパス（`ListPosition`。パスが見つからないときの代わりに添字も）・ヒットの添字だけ。**`FileEntryView*`/`FileEntryModel*` は持たない**（再スキャンで旧エントリが通知より前に破棄される）。起点（`Anchor`）と戻り先（`Origin`）は、`CursorMemo` と同じく**パス**で持ち、`ResolveRow()` で今の添字にする
- **「ディレクトリ移動」の判定は `reload_memo_` の有無**：購読（`ObservePath`）の中で、`FileListView::Reload()` の間だけ立つ `reload_memo_` が無い通知は移動とみなし、`search_.Clear()` する（カーソルを 0 に戻すのと同じ判定）。`FileListModel::Reload()` を `FileListView::Reload()` を介さずに呼ぶ処理を足すと、再スキャンなのに検索が消える。`TryJumpTo` は、同じパスへでも消す（ルートでの `navigate_left` など。無害）
- **メンバーの宣言順**：`search_` は `subscriptions_` より前に宣言する（購読の通知は `Fetch()` を呼び、`Fetch()` は `search_` を使う。破棄は宣言の逆順なので、購読が先に止まる）
- **遷移**（`SearchState`）：`Begin`（Idle/Committed → Typing。確定済みの語は Esc で戻れるよう取っておく。新しい語は空で、前のヒットは隠す）、`Commit`（Typing → Committed。**語が空なら `Cancel` と同じ**=検索を始める前の状態に戻る）、`Cancel`（Typing → 始める前の状態。カーソルを `Origin`（検索を始めた位置）へ戻すのは `FileListView::CancelSearch`。`Origin` は `Cancel` では消えず、`Clear` で消える）、`Clear`。**語が変わる遷移（`Begin`/`Cancel`/`Clear`、語が空の `Commit`）はヒットを空にする**ので、今の語のヒットが要るなら `RebuildSearchHits()` で作り直す（語がある普通の `Commit` は、語もヒットも変わらない）
- **入力中の動き**：打つたびに `Anchor`（最初は `/` を押した位置）から前方（ラップ）の最初のヒット（`Anchor` 自身を含む）へ。ヒットが無ければ `Anchor` に戻る。`↓`/`↑` は `Step(cursorIndex_)` で、動いた先を新しい `Anchor` にする（Esc の戻り先 `Origin` は動かさない）。**語を全部消したら、`Anchor` を `Origin` に戻す**（検索を始めた位置からやり直す）。`n`/`N`（`Step`）は、カーソルがヒット上でも、ヒットでない行でも、同じ式（カーソルの行そのものは含まない）
- **画面外へ飛ぶときだけ中央寄せ**（`JumpCursorTo`）：`Redraw()` のスクロールは行が見える最小限なので、遠くへ飛ぶと端に張り付く。飛ぶ前に行が見えていたか（`NSContainsRect(visibleRect, ...)`）を調べ、見えていなかったときだけ `scrollPoint:` で中央へ
- **ハイライトの描画**：`NSMutableAttributedString` に `NSBackgroundColorAttributeName` を付けて `drawInRect:`（実測：塗りは文字の行の高さ。20pt の行の中でほぼ中央）。カーソルのある行は `search_current`、ほかは `search_match`。カーソルの下線と同じく、**フォーカスのあるペインだけ** `search_current`。`Draw(min_y, max_y)` は、**描き直す範囲（`drawRect:` の `dirtyRect` の y）にかかる行だけ**描く（以前は全行を描いていた。行ごとに `file_size()` を呼ぶので、数万件で重い。1万件・全件ヒットで、描き直しが 2ms ほど、1打鍵の検索が 10ms ほど）
- **入力バーは、入力しているペインの下だけ**（ペインと同じ幅。反対側のペインには出ず、反対側の一覧も縮まない）：バーは `_MiataBrowserContainer` の子（`queryBars`。添字は ペイン番号 × 種類の数 + 種類）で、`layoutQueryBars` が、ペインの frame（`convertRect:` でコンテナの座標に直す）の下端から、種類の順（検索 → 絞り込み）に積む。位置が決まるのは `layoutOverlay` と同じで、`NSSplitView` のデリゲート（`splitViewDidResizeSubviews:`。ウィンドウのリサイズもディバイダのドラッグもここに来る）と、`setQueryBar:visible:` から。分割ビューは元のまま autoresizing で追従する。バーは**覆いより手前**（Quick Look で覆っているときも、バーが見える。覆いはペインの全体を覆うので、バーは覆いの下端に重なる）。バーの分だけ一覧を空けるのは、一覧の側（`FileListView::SetBottomInset` → `_MiataFileListLayoutContainer.footerHeight`。スクロール部分の高さが縮み、カーソルが見える位置までスクロールする）。バーの高さは `HeaderHeight()`（一覧が縮むのは、見えているバーの数 × この高さ）
- **バーの出入りは、そのペイン自身の状態だけで決まる**（`SyncQueryBars`）：その種類が `mode != Idle` のあいだ、そのペインの一覧を縮めて（見えているバーの数だけ）、そのバーを出す。中身（検索語・件数）もそのペインのもの。カーソルのペインには依存しないので、`h`/`l` でペインを切り替えても、一覧の高さは変わらず、バーの内容も変わらない。以前は、バーを全幅に1つだけ出し、「どちらかのペインに検索があれば出し続ける」ことで切り替えのガタつきを避けていたが、反対側のペインまで縮み、検索の無いペインにカーソルがあると空の帯が出るので、ペインごとにした
- **罠：入力欄が first responder を持つ間は `MiataRootView::keyDown:` が呼ばれない**（Normal のキーバインドも効かない）。Enter/Esc/↑↓/Tab は delegate の `doCommandBySelector:` で横取りする。Enter/Esc は `dispatch_async` で次のランループへ（確定・取り消しで first responder を手放す処理を、`doCommandBySelector:` の呼び出しの中で行わないため。`FilterListDialog.mm` は、閉じる過程で delegate 自身が破棄されるため、同じく逃がしている）。Tab は握りつぶす（キービューループで入力欄を失う）。**IME の変換中**（`hasMarkedText`）は、検索語にしない（読みの途中の文字を追いかけて、カーソルが飛び回る）。文字を読む `QueryBar::SettledText()` が、入力中で変換中でないときだけ返し、`BrowserView::PullQuery()` がそれを語に取り込む（通知の `controlTextDidChange:` と、毎ティックの照合 `ReconcileInput` の両方が、同じ入口を通る。通知の取りこぼしは、ティックが拾う）
- **罠：`DialogPanel::Hide()` は first responder を無条件に `MiataRootView` へ戻す**（`Dialog.mm`）。入力中にダイアログ（ファイル操作の失敗の通知など）が閉じると、入力欄が first responder を失うが、バーは入力中のまま、打鍵が Normal のキーバインドへ流れる。対策は2つ：(1) `View::OpenNextDialogIfNeeded` が、**ダイアログを開く直前に**入力中の検索・絞り込みを成り行きで終わらせる（`SettleQueryInput`。入力欄を持ったままだと、ダイアログ向けの Enter/Esc を入力欄の delegate が受けてしまう）、(2) 毎ティックの `BrowserView::UpdateQueryBars` が、入力欄と各ペインの状態を突き合わせて整える（`UpdateQuickLook` と同じ「状態を見て判断する」方式）：入力欄が first responder を失っていれば入力を終わらせる（`ReconcileInput`）。`controlTextDidEndEditing:` は使わない（毎ティックの照合で足りるうえ、通知の中から `makeFirstResponder:` を呼ぶと再入しうる）。**状態を先に落としてから `makeFirstResponder:` を呼ぶ**（再入しても何もしない）
- **罠：入力欄を first responder にするのは、バーを出した後／バーを隠すのは、手放した後**：隠れたビューは文字を受けられず、first responder を持ったまま隠すとキー入力が beep になる。`BeginInput(kind)` は `SyncQueryBars()`（バーの出入りと中身だけを合わせる。状態は変えない）→ `QueryBar::BeginInput()` の順。ここで `UpdateQueryBars()`（`ReconcileInput` を含む）を使うと、入力欄がまだ first responder でないので、「フォーカスを失った」と誤って確定する。手放すのは `ReconcileInput`（バーを隠す `SyncQueryBars` より先）
- **確定後の入力欄は、編集不可・選択不可・`refusesFirstResponder`**、バー全体の `hitTest:` が自分を返す（`_MiataQuickLookShield` と同じ考え方）。クリックで first responder を奪われると、キー入力が `MiataRootView` に届かなくなる。入力中だけ `hitTest:` を通常に戻す（キャレットを動かせるように）
- **罠：確定後の入力欄の文字が、フォントによっては、ラベル（プロンプト・件数）より上にずれる**（実機で、`set_font("Osaka")` + `set_font_size(20)` のときに報告された。システムフォントでは出ない）。原因は、入力欄のセルの**単一行モード**（`usesSingleLineMode`）を、確定後も `YES` のままにしていたこと：ラベルは `NO`（`labelWithString:` の設定）で、同じ文字でも、単一行モードのセルは、行間の大きいフォントで、文字が上に寄って描かれる（実測: Osaka 20pt・2 倍の解像度で、重心が 11 画素=5.5pt 上。フォントによっては 11.7pt。システムフォント以外の 9 種のフォントすべて）。**入力中は単一行モードが要る**（外すと、Option+Return などで欄に改行が入り、入力欄のエディタが何行にも伸びる=17pt から 75pt。実測）ので、`QueryBar::Impl::SetEditable` が、**入力中だけ `YES`、確定後は `NO`** に切り替える（`scrollable` は、残してもずれない=実測なので、作るときに 1 回だけ設定する）。入力中に切り替える順序は、`BeginInput` が `SetEditable(true)` の後に `makeFirstResponder:`、`EndInput` が `makeFirstResponder:` の後に `SetEditable(false)`（編集の最中に変えない）。**この種の見た目の確認は、フォントを変えて、実際に描いて測る**：`query_bar_test` の `alignment`（プロンプトと同じ文字列を入力欄に入れて、墨の重心・上端・下端を比べる。実機と同じ Osaka 20pt・2 倍の解像度で走らせる=`run_qbar.sh` が `alignment` だけに設定を渡す。既定のフォントでは、修正前でも通ってしまう）と、`single_line`（入力中は改行が入らず、高さが変わらない。確定後はラベルと同じ設定）。全体の確認は、`align_matrix.py`（フォント 10 種 × サイズ 7 通り × 倍率 2 通り × 検索・絞り込み。修正前は 560 行中 228 行が許容を超え、修正後は 0 行。重心の差の最大は 0.17pt。常用の回帰テストには入れない=70 秒かかる）
- **罠：フィールドエディタ（`NSTextView`）はウィンドウの全テキスト欄が共有する**：入力中のキャレットの色（`insertionPointColor`）を変えると、次に別の入力欄（リネームなどのダイアログ）が同じエディタを使うときにも残る（実測）。`BeginInput` で元の色を控え、`EndInput` で戻す（入力欄が first responder を奪われた後でも、`[window fieldEditor:NO forObject:nil]` で共有のエディタを取れる）。`stringValue` も、編集が終わるまで欄に取り込まれず、終わると取り込まれて残る（以前は、取り消した語が、検索の無いペインの空の帯に残った）ので、`QueryBar::Update` は、覚えていた値ではなく、**欄の実際の中身と比べる**
- **罠：ビューの `drawRect:` で `dirtyRect` をそのまま塗らない**（`NSIntersectionRect(dirtyRect, self.bounds)` を取る）。macOS 14 以降、ビューは既定で自分の範囲に描画を切り詰めない。親をまるごとビットマップに描く（`cacheDisplayInRect:`）と、`dirtyRect` が子の範囲を超えて渡され、不透明に塗る子（バー）が、隣のビュー（一覧）を塗りつぶす。画面への通常の描画では、dirty 領域が範囲内に収まるので気づきにくい（ヘッドレスの描画テストで発覚した）。`_MiataQuickLookShield::drawRect:` も、以前は `dirtyRect` をそのまま塗っていた（覆いが片側のペインだけのとき、親をまるごと描くと、反対側の一覧まで塗りつぶされることをハーネスで確認した）ので、同じ対策を入れた
- **Esc**：入力中は検索の取り消し（入力欄が受ける。Quick Look は閉じない）。通常時の Esc（`navigate_cancel` → `View::NavigateForBrowser` の `Cancel`）は、プレビューを閉じ、カーソルのペインの検索を消す（`ClearSearch`）。1回で両方。**絞り込みは解除しない**（後述「絞り込み（フィルタ）」）
- **`n`/`N` が動けないとき（検索なし・ヒット0件）は beep**（`lua_command_search_next/prev`）。ダイアログの表示中は、検索を始められず（`View::BeginSearch` が false）、`n`/`N` も動かない
- **空の一覧**：検索は始められ（ヒット0）、`GetCurrent()` ではなく `CurrentPath()` と `list_` のサイズで扱う。空のディレクトリ（ファイルもフォルダも1つも無い）で、`GetCurrent()` を無ガードで呼ぶ箇所があり（`View` の `Mark`/`Unmark`/`ToggleMark`、`NavigateForBrowser` の `Ok`）、マークや Enter で落ちていた。直した内容は、後述「空のディレクトリ」（`GetCurrent()` 自体は、いまは削除した）

## 絞り込み（フィルタ）

`Miata.command.filter([mode])` / `filter_set(query, [pane], [mode])` / `filter_clear([pane])`（`Application.cc` の `lua_command_filter*`）→ `View::BeginFilter` / `SetFilter` / `ClearFilter` → `BrowserView` → `FileListView`。`f`（`resources/test.lua`）でペインの下（検索バーの上）に入力欄が出て、打つたびに、名前に語を含む行だけが一覧に残り、一致部分が強調される（部分一致）。`F`（`<S-f>`）は、あいまい一致（外部の fzf。下記）。ユーザー向けの仕様は README の「絞り込み」。ここには、設計の決定と罠を書く。`dialog_filter_list`（`fzf` で候補を選ぶダイアログ）とは別物。

- **`list_` を、絞り込み後の行だけにする**：画面の行番号（`cursorIndex_`・検索のヒット・まとめてマーク・ドラッグ・Quick Look・`Draw`・Lua の `cursor_entry` / `marked_entries`）は、すべて `list_` の添字。「全行 + 見える行のマスク」の案は、添字の空間が二重になり、全部の参照が壊れるので採らなかった。全エントリ（ソート済み）は `sorted_`、`sorted_[i]` が `list_` の何行目か（隠れていれば -1）は `row_of_sorted_`。**`list_` を書くのは `ApplyFilter()` だけ**（`Fetch()` が `entries_` → `sorted_`（ソート）→ `ApplyFilter()`。語が変わるときは `ApplyFilter()` だけを走らせ、再ソートしない：ソートの比較は呼ぶたびに NSString を作るので重い）。`ApplyFilter()` は最後に `RebuildSearchHits()` を呼ぶ（検索の対象は、絞り込み後の行）。**行番号（`list_` の添字）を持つ機能を足すときは、`ApplyFilter()` で作り直すこと**。`list_` は「最終的な表示順」で、`sorted_` の部分列とは決め打ちしない（将来、あいまい一致で得点順に並べるときは、`ApplyFilter()` に並べ替えの段を足すだけで済む。カーソルの追従が `row_of_sorted_` を使うのもこのため）
- **メンバーの宣言順**：`sorted_` / `row_of_sorted_` / `filter_` は `subscriptions_` より前に宣言する（購読の通知は `Fetch()` を呼び、`Fetch()` は `filter_` を使う）。ディレクトリ移動の判定は検索と同じ `reload_memo_` の有無で、購読の中で `search_.Clear()` と並べて `filter_.Clear()`（再スキャン=リロード・ソートでは保つ）
- **3つに分けた**：`FilterState`（AppKit 非依存。遷移、基準の位置（`Anchor` / `Origin`）、行ごとの一致箇所だけ。マッチ自体は持たない）、`NameMatcher`（語 → 名前の一致箇所（UTF-16）。検索と共用）、`FileListView`（一覧の作り直し・カーソル・描画）。`SearchState` を読み替えて流用する案は採らなかった：ヒットが「見えている全行」になって `Step` / `Ordinal` が要らなくなり、語が空のときの意味も違う。共通の核（`QueryState`）や、種類ごとのインターフェースも作っていない（実装が2つのうちは、遷移を50行ずつ持つほうが単純）
- **語が空は「絞り込みなし」（全行）**：入力を始めた直後（`Begin`）は語が空なので、確定済みの絞り込みがあっても、`f` を押した瞬間に全行に戻る（画面に見えている状態と、そのまま Enter で確定される状態が常に一致する）。Esc（`Cancel`）で前の絞り込みに戻る。**語が空のまま Enter は解除**（`FilterState::Commit` の空の分岐。検索の `Commit` は「始める前の状態に戻る」）。通常時の Esc は絞り込みを解除しない（`NavigateForBrowser` の `Cancel` は絞り込みに触れない）。どれもユーザーの決定
- **成り行きで終わるときは、語が空なら取り消す**（`BrowserView::FinishTyping(target, explicit_enter)`）：ダイアログが開く直前（`SettleQueryInput`）・ペインの切り替え・入力欄が first responder を失った（`ReconcileInput`）で入力が終わるとき、語が空だと、解除ではなく取り消し（前の絞り込みに戻る）。空で確定=解除は、ユーザーが Enter で押したときだけ（`on_commit` が `explicit_enter = true`）。そうしないと、絞り込み済みで `f` を押した直後に、ファイル操作の失敗のダイアログが割り込んだだけで、前の絞り込みが黙って消える。**入力欄が first responder を持たない入力中の状態は、毎ティックの整合処理が終わらせる**（`FileListView::BeginFilter()` を直接呼んで入力中にし、ティックを回すと確定される。テストは、必ずバー経由で始める）
- **カーソルは「基準」を追う**：打つたびに一覧が変わるので、画面のカーソル（行の添字）ではなく、基準（`Anchor`。最初は `f` を押したときのカーソルのファイル）のファイルを追う。位置は `ListPosition`（パスと、**絞り込む前の全体の並び `sorted_` の添字**）で持ち、`RefilterAround(pivot)` が、`sorted_` で pivot 以降に最初に見える行 → 無ければ手前で最後 → 無ければ 0、へ寄せる（`NearestShownRow`。純関数）。基準のファイルが見えていれば、そこに留まる。0件でも基準は失わない（語を戻せば、元の付近に戻る。0件で確定した後の解除や `f` でも。一覧が空のときは `CursorOrAnchor()` が基準を引き継ぐ）。↓↑（`StepFilter`）は一覧のカーソルを1行動かして、動いた先を新しい基準にする（折り返さない）。**語を全部消しても、基準は戻さない**（検索の「始めた位置からやり直す」と違い、絞り込みは「カーソルがファイルに付いていく」）。Esc は `Origin`（始めたファイル）へ。解除は今のファイル（0件だったときは基準のファイル）に留まる。**0件のペインを再読み込み（手動・自動）して、語に合うファイルが現れたときも、カーソルは基準のファイルの近くへ寄る**（`RestoreCursor` は、再スキャン前の一覧が空なら `ShownRowNear(filter_.Anchor())`。絞り込んでいなければ基準は空で先頭。`CursorMemo` は `list_` から作るので、0件だと空になり、以前は基準を無視して先頭に着いた。コードレビューで見つかった）。「基準の近くの見えている行」を求める `ShownRowNear` は、`RefilterAround` と共有する（`ApplyFilter()` の後に呼ぶ：`row_of_sorted_` を読むため）。位置の `row` は同じ世代（`Fetch()` から次の `Fetch()`）の中でしか合わない：`ResolveSortedIndex` は、まず控えた添字がパスと合うかを見て、合わなければパスで探し、それも無ければ添字を丸める
- **再読み込み（手動・自動）とソートは絞り込みを保つ**：`Reload()` のカーソル復元の記録（`CursorMemo`）は `list_`（絞り込み後）の順で控え、`Fetch()` が絞り込みを再適用してから、`RestoreCursor` が、その一覧の中で復元する。新しく一致するファイルは現れ、一致しなくなったファイルは消える。隠れたマークは、モデルの再スキャンがパスで引き継ぐ。ディレクトリを移動したら解除（検索と同じ）。保存はしない（`PaneState` に入れない）
- **隠れたマーク：操作の対象は「見えているマーク」だけ**（ユーザーの決定）：コピー・移動（既定の `c` / `m`: `targets()` → `copy_to` / `move_to`）・ゴミ箱（既定の `dd`: `marked_entries` → `trash`）・リネーム（既定の `r` の「見えているマークがあるか」= `marked_entries()` の空）は、モデルの全エントリではなく `FileListView::MarkedEntries()`（`list_` のマーク）で対象を決める（`Application.cc` の `MarkedPaths` / `AnyVisibleMarked`）。隠れた行のマークは残り、対象にならない。見えているマークが0件なら、コピー・移動はカーソル下の1件（隠れたマークは無視）、ゴミ箱は何もしない、リネームはカーソルのファイルを改名できる。**完了後に外すのは、操作したファイルのマークだけ**：`FileOperationCompleted::sources`（開始時の対象）を `UnmarkPaths` で外す（以前はそのペインの全マークを外していたので、操作の最中に付けたマークや隠れたマークまで消えた）。絞り込みを変えながらコピーしても、開始時の対象だけが外れる。ドラッグの `EndDrag` も、運んだパスだけ。移動（Move）は、再スキャン（`ReloadDirectory`）がパスでマークを引き継ぐので変えない。削除の確認文に、隠れたマークがあれば「(絞り込みで隠れているマーク N 件は対象外です)」を添える。バーの右端にも「隠れたマーク N」を出す（`HiddenMarkCount`。毎ティック `SyncQueryBars` が更新）。**この配管（操作の対象の差し替え）は、絞り込み本体より先に入れる**：本体が先だと、隠れたマークを誤って消す中間状態ができる
- **バーは2段**：ペインの下端から、検索 → 絞り込みの順に積む（`layoutQueryBars`）。両方出ていれば、一覧は2段分縮む。入力は全体で常に1つ（first responder が1つ）：`TypingTarget()` が4スロット（ペイン × 種類）から探す。種類ごとの違いは、`BrowserView.mm` の無名名前空間の `switch`（`PromptOf` / `ModeOf` / `BeginOf` / `SetQueryOf` / `StepOf` / `CommitOf` / `CancelOf` / `DisplayOf`）に集めた。種類を足すときは、`constants::kQueryKinds` と、これらの `switch` に足す（足し忘れはコンパイラが警告する）。プロンプトは「絞り込み」、件数は「見えている行数/全行数」（0件は「見つかりません」）+「  隠れたマーク N」（`FilterCountText`）。IME・Enter/Esc/Tab・first responder・キャレットの色の罠は、検索と同じ部品（`QueryBar`・`BrowserView`）で、1実装のまま両方に効く（前述「ファイル名の検索」）
- **ハイライト**：絞り込みの一致箇所（`filter_match`）を先に、検索の一致箇所（`search_match` / `search_current`）を後に塗る（同じ文字に両方当たれば、検索の色）。絞り込みに「カーソルのある行」の色は無い。一致箇所は `FilterState` が `list_` と同じ並びで持つ（`ApplyFilter` が作る）
- **あいまい一致は、外部の fzf（`FzfFilter`）に任せる**（ユーザーの決定。最初は、fzf のアルゴリズム（`algo.go` の `FuzzyMatchV2`）を C++ に移植して、一致位置も出す案を調べた。「外部コマンドとしての fzf でよい。あいまい一致では一致位置を出さなくてよい」となったので、採らなかった）。`MatchKind`（`Substring` / `Fuzzy`）は、入力を始めるときに決まる（`FilterState::Begin(origin, kind)`）：確定済みの絞り込みを取っておくとき（Esc で戻る）、語と一緒に一致のしかたも取っておく（`Saved{query, kind}`）。入力中に別の `filter(...)` を呼んでも、始まらない（変わらない）。Idle は部分一致で、語が空のまま確定=解除・取り消しで Idle に戻る・`Clear` は、部分一致に戻す。バーのプロンプトは、部分一致が「絞り込み」、あいまい一致が「あいまい」（`QueryBar::Display::prompt`。空なら変えない。`BrowserView.mm` の `FilterPromptOf`）。Lua の `mode` は `"substring"`（省略・nil も）/ `"fuzzy"`、それ以外・文字列でない値はエラー（`OptionalMatchKindArg`。`luaL_error` の前にオブジェクトを作らない）
- **あいまい一致の作り**：`ApplyFilter()` の枝（`Kind() == Fuzzy` かつ語がある）が、`FuzzySource().FilterIndices(語)` の返す候補の添字（fzf の出力の順=得点順）で `list_` と `row_of_sorted_` を作る。**一致箇所（`ranges`）は空のまま**（強調しない。fzf の `--filter` は位置を出さない）。`FuzzySource()` は `sorted_` の名前を候補にした `FzfFilter` で、`Fetch()` のたびに捨てて、必要になったとき作る（候補を一時ファイルに書き出すのは作るとき 1 回。語が変わるたびに fzf を起動する）。fzf には `sorted_` の順に候補を渡すので、得点が同じ行（fzf の既定のタイブレーク: 短い候補が先、同じ長さなら入力の順）は、ソートの順になる。**カーソルは、語が変わるたびに先頭の行へ**（`RefilterToTop`。基準も、その行のファイルにする。0 件のときは、カーソルも基準も動かさない）：「基準を追う」は、得点順だと、語を打つたびにカーソルが一覧の下のほうに取り残される（fzf では、いちばん一致する行が選ばれている）。語が空になれば、通常の「基準を追う」に戻る（全行がソートの順に出て、カーソルは直前の先頭のファイルのまま）。非対話の `SetFilter(…, Fuzzy)` も先頭へ。**`list_` の順は、ソートの順とは限らない**ので、行の添字（`ListPosition::row` ほか）は `sorted_` の添字と取り違えないこと（`row_of_sorted_` が対応を持つ）。再読み込み・ソートでは `RestoreCursor` が同じファイルに留める（先頭へは飛ばない）
- **`FzfFilter` の作り**：一時ファイル名は `miata-fzf-<pid>-<連番>.txt`（左右のペインとダイアログが同時に持つので、以前の pid だけの名前だと、互いのファイルを上書き・削除した）。改行（`\n` `\r`）を含む候補は、空白に置き換える（fzf は行単位）。`FilterIndices(query)` は、出力の行を候補の添字に戻す（同じ文字列の候補は、候補の順に 1 件ずつ使う。fzf は同じ文字列を入力の順に出す）。fzf が無い・起動に失敗・時間切れ（10 秒）のときは、`SubstringFallback`（ASCII の大文字小文字を無視した部分一致、候補の順）。`UsesFzf()` が false のとき `FilterStatus::fuzzy_fallback` が立ち、バーの件数に「fzfなし(部分一致)」を足す（黙って部分一致になる罠を避ける）。クエリは `{"--filter", query}` で渡す（`-` や `--` で始まる語も、語として扱われる。実測：`--version` も実行されない）。**fzf の拡張検索の構文がそのまま効く**（空白で AND、`^` `$` `'` `!` `|`）。**`FZF_DEFAULT_OPTS` も効く**（`--exact` や `--no-sort` を入れていると結果が変わる。実測。起動した環境のものを継承する）。fzf の場所は `pl_find_executable("fzf")`（`PATH`、`/opt/homebrew/bin`、`/usr/local/bin`、`/usr/bin`）
- **限界（あいまい一致）**：一致位置を強調しない。語を打つたびに、fzf を同期で起動して待つ（メインスレッドが止まる。fzf 単体の実測: 1 万件 5〜10 ms、10 万件 9〜64 ms。Miata から 1 万件で 1 打鍵 5 ms ほど=部分一致と同じ）。得点の付け方は fzf のバージョンで変わりうる（確認したのは 0.74.4）。**一致位置が欲しくなったら**：`algo.go` の `FuzzyMatchV2`（前処理 → 位置ごとのボーナス → スコア行列 → バックトレース。1〜2 文字の ASCII の速い経路は、一般の経路と同じ結果になるように作られている）を C++ に移植して、`NameMatcher` に足す（`FzfFilter` と並べて、出力の順と突き合わせられる。MIT ライセンスなので、表示が要る）
- **照合**：`NameMatcher`。部分一致。語に大文字（Unicode の大文字を含む）が1文字でもあれば大小を区別、無ければ区別しない（スマートケース。検索と同じ）。`NSLiteralSearch` は付けない（NFC と NFD が一致する）。範囲の長さは名前の側の長さ。全角/半角・ひらがな/カタカナ・アクセントは畳み込まない。語が空・不正な UTF-8 は `Empty()`（絞り込みでは全行、検索ではヒット無し）。外部の `fzf --filter` は、一致位置を返さず、結果がスコア順の文字列なので、ハイライトに使えない（だから、あいまい一致は強調しない。上記）。「語を延ばしただけなら前の `list_` の部分集合」という差分の絞り込みは、結合文字を足すと一致が増えうる（`e` + U+0301 → `é`）ので、単調ではなく、採らなかった
- **Lua**：`filter([mode])`（入力を始める。ダイアログの表示中・すでに入力中は false）、`filter_set(query, [pane], [mode])`（入力欄を使わずに確定済みにする。空で解除。戻り値は `shown, total`。入力中なら先に終わらせる。NUL はエラー、不正な UTF-8 は `RepairUtf8`。ダイアログの表示中でも動く）、`filter_clear([pane])`（解除。絞り込んでいたら true。ダイアログの表示中でも動く）。`filter_set` / `filter_clear` を `IsAnyDialogOpened()` で止めないのは `jump_to` と同じ理由（`dialog_input` を閉じた直後のティックでは、閉じたはずのダイアログがまだ開いている扱い）。同名の Lua 関数は `base.lua` に作らない（C++ が無言で上書きする）。`luaL_error` の前に、デストラクタを持つオブジェクトを作らない
- **限界**：絞り込みで隠れる新規ファイル（作成・リネーム・コピー先）は、語に合わなければ一覧に出ない。1打鍵ごとに全エントリを照合し直す（1万件で数 ms〜10 ms。5万件・10万件は未実測）。名前以外（サイズ・更新日時など）では絞り込めない

## 外部コマンドの起動（`pl_run_process`）

`pl_run_process(executable, args, stdin_file, timeout_seconds = 10)`（`platform.h` / `osx.mm`）。標準入力をファイルから読ませて、標準出力を回収する（標準エラーは捨てる。環境変数は継承する）。使うのは `FzfFilter` だけ（`dialog_filter_list` と、絞り込みのあいまい一致）。

- **`NSTask` を使わない**：`waitUntilExit` が、待つ間に**実行ループを回す**。実測（fzf を 100 回、5 ms のタイマーを置いて）：1 回 **84 ms**（入力が 1 万行。fzf 自体は 6 ms）、**78 ms**（入力が 10 行）かかり、タイマーが呼び出しの最中に 100 回で 1420 回ほど発火した（本番では、0.05 秒のタイマー=`Application::Update()` が、呼び出し元の更新の途中に再入する。再スキャンやバーの整合処理が、`list_` を作り直している最中に走りうる）。`posix_spawn` + 自前の待ちにして、1 回 **5〜6 ms**、発火 0 回、出力は同一になった。`dialog_filter_list` は、これまで打鍵ごとに 80 ms ほど待たされていた（入力の大きさによらない）
- **作り**：`posix_spawn` のファイル操作で、標準入力=ファイル、標準出力=パイプ、標準エラー=`/dev/null`。`POSIX_SPAWN_CLOEXEC_DEFAULT` で、0/1/2 以外の記述子は子に渡さない。シグナルのマスクは空に、シグナルの処理は既定に戻す（呼び出し元が `SIGPIPE` を無視していても、子に引き継がない）。標準出力は EOF まで読む（先に子の終了を待つと、出力がパイプのバッファを超えたとき、子と親が互いを待って止まる）。`poll` で期限を見て、期限を過ぎたら `SIGKILL`。EOF の後の終了待ちも期限つき（`waitpid(WNOHANG)` を 0.2 ms 刻みで。標準出力を閉じても終わらない子で、`waitpid` のブロックに固まらないため）。期限切れは `unexpected("timed out")`（`FzfFilter` は部分一致にフォールバック）。終了コードは、シグナルで終わったときは 128 + シグナル番号。起動の失敗（実行ファイルが無い・入力ファイルを開けない）は `unexpected`
- **罠**：(a) テストで「子が残っていないこと」を `pgrep -x 名前` の数で見る（呼び出しの前後で比べる）。(b) 子に `SIGPIPE` の無視が引き継がれていないかを `/bin/sh` の `trap -p` で見ても分からない（起動時に無視されていたシグナルは出ない）：perl の `$SIG{PIPE}`（`IGNORE` と見える）で見る。(c) 子の標準エラーが閉じていないかを perl の `fileno` で見ても分からない（perl が閉じた標準の記述子を自分で補う）：`sh` で `/dev/fd/2` があるかを見る。**`POSIX_SPAWN_CLOEXEC_DEFAULT` は、ファイル操作に書いていない 0/1/2 も閉じる**ので、標準エラーを `/dev/null` に開くファイル操作を外すと、子の fd 2 が閉じる（子が最初に開いたファイルが fd 2 になり、以降のエラー出力がそこへ混ざる）。(d) 変異テストでは、起動に失敗しても pid が 0 のまま `kill` / `waitpid` するような壊し方を作らない（`kill(0, SIGKILL)` は、テストを走らせているプロセスグループごと殺す）。(e) 冗長な設定が残る：パイプの `FD_CLOEXEC` と標準入力の `O_CLOEXEC` は、`CLOEXEC_DEFAULT` があるので、`posix_spawn` に対しては不要（ほかの起動手段=別スレッドの `fork` / `exec` への備え。これらを外す変異は作っていない。作れば生き残るはず）
