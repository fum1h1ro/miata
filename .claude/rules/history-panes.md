## フォルダの履歴（ヒストリ）

`Miata.command.history([pane])`（`resources/base.lua` の Lua。`history_list` で履歴を取り、`dialog_filter_list` で選ばせ、`jump_to` で移る）→ `lua_command_history_list` / `lua_command_jump_to`（`Application.cc`）→ `View::JumpToPath` → `FileListModel::TryJumpTo`。ユーザー向けの仕様は README の「フォルダの履歴」。ここには、設計の決定と罠を書く。**履歴は左右のペインで 1 つ**（最初はペインごとに別々に持っていたが、どちらのペインで行ったフォルダも、どちらからでも選べるほうが使いやすいので、1 つにまとめた。2026-10-02）。

- **4つに分けた**：`PathHistory`（`models/`。AppKit・Lua・Config・Pane のどれも知らない純ロジック。`BrowserModel` が値メンバー `history_` で1つ持つ）、記録のタイミング（`FileListModel::TryJumpTo` の成功経路の1か所。左右の `FileListModel` は、コンストラクタで渡された `PathHistory*` に記録する。`nullptr` なら記録しない=テスト用）、保存と復元（`BrowserModel::RestoreHistory(limit)` / `SaveHistoryIfChanged()`。キーは `MiataHistory` の1つ。`Application` が配線する）、見せ方（Lua の `history`）。**`BrowserModel` のメンバーの宣言順**：`history_` は `left_` / `right_` より前に置く（両方のコンストラクタにポインタを渡す。メンバーは宣言順に構築される）
- **記録点は `TryJumpTo` の成功経路だけ**（通知 `path_.Value` の直前に `history_.Record(path)`。購読側が履歴を読んでも、この移動が入っている）。ユーザー操作の移動（Enter・親へ戻る・履歴ジャンプ）は、すべてここを通る。`JumpTo`（`FileListModel` のコンストラクタが入れる、起動時のホーム）・`TryRestoreTo`（起動時の、前回のペインの場所の復元）・`Reload`・ソートは通らないので、記録されない。失敗した移動は、`TryJumpTo` が何にも触れずに返るので記録されない。**`ObservePath` を購読して履歴を作らない**：`ReactiveProperty::Value()` は同じ値でも毎回通知し、`rxcpp::subjects::behavior` は購読時に現在値を再生するので、再スキャンと起動時の初期値が混ざる（区別できるのは `FileListView::reload_memo_` の有無だけ）
- **`PathHistory` が不変条件を持つ**（`Key()` に集約）：絶対パス・改行/CR/NUL を含まない（`FzfFilter` は候補を改行で区切るので、含まれると割れる）・末尾の `/` なし（`std::filesystem::path` は `"/tmp/"` と `"/tmp"` を別物と比べる）・重複なし・上限以下。正規化は末尾の `/` だけ。`lexically_normal` は、シンボリックリンクを経由した `..` を壊すので使わない。`realpath` / `canonical` もしない（`/tmp` を選んだのに `/private/tmp` へ移る驚きがある）。**NFC にもしない**：画面の操作で作られるパスは、一覧の名前（`Name()` = NFC）で組み立てる（`Path() / Name()`）ので、同じフォルダの綴りは揺れない。`pl_normalize_string` も使わない：不正な UTF-8 のバイトを U+FFFD に置き換える（後述「名前が UTF-8 として不正なファイル」）ので、Lua の `jump_to` に渡された、実在する（APFS 以外の）パスが、別のパスに変わってしまう
- **上限の注入**：モデルは `Config` を知らない（`Config.h` は Lua に依存する）。上限は、左右を合わせた件数。`PathHistory` の上限は、注入されるまで 0（何も記録しない）で、`Application::InitializeImpl` が `View` を作った直後（タイマーが動き出す前=最初の移動より前）に `BrowserModel::RestoreHistory(Config::HistoryLimit())` で渡す（設定は `View` を作る前に読み込み済み）。`SetLimit` は縮めたら古い方から捨て、広げても戻らない。**0 は、保存してあった履歴も消す**（`Restore` が空にして Dirty にし、次のティックの保存でキーが消える。「オフ」と「ディスクにも残さない」をそろえた）。**設定の読み込みでエラーが起きた起動では、最大値（`kHistoryLimitMax`）で復元する**：構文エラーのファイルは1行も実行されず、実行時エラーの行より後の設定も実行されないので、ユーザーが指定した上限（`set_history_limit(300)` など）が反映されず、既定の100で復元すると、保存してあった履歴が捨てられ、最初のティックで上書きされてしまうため（設定を直して起動し直したときに、正しい上限が適用される）
- **保存は NSUserDefaults、毎ティックの dirty 検知**：`Application::Update()` の最後の方（ペインの状態の保存の前）が `SaveHistoryIfChanged()` を呼び、`Dirty()` なら `pl_save_string_list` する（`UpdateAutoReload` などと同じ「状態を見て判断する」方式。終了フックが無いので、終了時にまとめて保存できない。ウィンドウ位置の autosave も、変更のたびに保存する方式）。連続した移動は、ティックごとに1回にまとまる。**実測**：保存の直後に SIGKILL しても残った（30回中30回）ので、`synchronize` は呼ばない。上限10000件の保存は約20ms、読み込みは約4ms。形式は `MiataHistory` キーの `NSArray<NSString*>`（新しい順）。壊れたデータへの防御は2段：`pl_load_string_list` が型を検査する（配列でなければ空、文字列でない要素は捨てる）、`PathHistory::Restore` が内容を検査する（相対パス・重複・上限超過を捨てる。整えた結果が保存してあったものと違えば Dirty にして保存し直す）。`pl_save_string_list` は、空の配列でキーを消し、`stringWithUTF8String:` が nil になる要素（不正な UTF-8）を捨てる（nil を配列に入れると例外になる）。`pl_read_file` は存在しないファイルに使えない（`tellg()` が -1 になり、コードの上では未定義動作。未実測）ので、履歴の保存には流用しない
- **`jump_to` / `View::JumpToPath` は、`IsAnyDialogOpened()` や `View::Navigate`（ダイアログ表示中はダイアログに回す）でガードしない**：`Application::Update()` は `Script::Update()`（Lua のコルーチンの再開）→ `CheckDialogState()` の順なので、`dialog_filter_list` を閉じた直後のティックでは、閉じたはずのダイアログがまだ `current_dialog_` に残っていて、`IsAnyDialogOpened()` が true のまま `jump_to` が呼ばれる。失敗は `JumpToOrReport`（`ReportFileError`。権限の失敗には許可の案内が付く。`RequestDialog` はキューに積むだけで、次の `CheckDialogState` で開く）に通し、移った後に `browser_->UpdateQueryBars()` を呼ぶ（移動で検索と絞り込みは消えるので、バーを次のティックを待たずに閉じる。`NavigateForBrowser` の末尾と同じ）
- **履歴から外すのは、フォルダが無いと確かめられたときだけ**（`View::JumpToPath` の `IsKnownNotDirectory`）：移動に失敗し、かつ `std::filesystem::status` が `not_found` か、フォルダ以外（ファイルになった）のとき。`status` 自体が失敗するとき（親が通れない、一時的な I/O エラー、シンボリックリンクの循環、ネットワークの切断中など）は有無が分からないので外さない。仕様は「権限以外の失敗はすべて外す」ではなく「もう無いとき」。`FileError::permission_denied` は見ない：権限が無い失敗でも、フォルダ自体は `status` で調べられる（存在する）か、調べられない（外さない）かのどちらかで、`status` が「無い」を返す権限の失敗は作れなかった（見ても結果が変わらない冗長な条件になる。変異テストで確かめた）
- **`dialog_filter_list` から戻る側の Lua**：`history` は、コルーチンの最初に `pane` を決めて、`history_list` と `jump_to` の両方に渡す（ダイアログを開いている間にフォーカスが動いても、開いた時点のペインを移す）。履歴が空なら `dialog_confirm("履歴がありません")` だけ（空の絞り込みダイアログは開かない）。ダイアログの表示も戻り値も同じ文字列（添字は返らない）なので、`items` にはフルパスをそのまま渡す
- **`luaL_error` は longjmp**（Lua は C としてビルドされている。`packages/CMakeLists.txt`）：C++ のオブジェクト（`std::string` など）を持ったまま呼ぶと、デストラクタが走らない。新しいコマンドは、引数を検証して `luaL_error` を呼んでから、オブジェクトを作る（`lua_command_jump_to`、`Config::lua_set_history_limit`、`OptionalPaneArg`）。既存の `lua_command_bind` は持ったまま呼んでいるが、真似しない
- **`jump_to` のパスは「平らな絶対パス」だけ**（`IsPlainAbsolutePath`。空の要素（`//`）・`.`・`..` を含むとエラー）：`NavigateToParent` は `parent_path()`（字句上の親）を使うので、`/a/b/..` を開くと、そのあとの `h` が `/a` ではなく `/a/b` へ移る。履歴の `Key()` の正規化は、末尾の `/` だけ（`lexically_normal` は、シンボリックリンク経由の `..` を壊すので使わない）なので、入口で弾く。判定は `std::string_view` だけで行う（`luaL_error` の前に、デストラクタを持つオブジェクトを作らない）
- **名前**：Lua の `history` と、C++ の `history_list` / `jump_to` は別のキー（同名だと、C++ が Lua の関数を無言で上書きする）。`jump_to` の仕様（絶対パスのみ・`~` は展開しない・失敗時に履歴から外れうる）は、README に書いた。ペイン引数は `OptionalPaneArg(L, index, fallback)`（`Application.cc`。`reload` / `history_list` / `jump_to` で共有）
- **`set_history_limit`**：既存の設定で初めて値の範囲を検証する（`lua_tointegerx` で整数かどうかを見て、0〜`Config::kHistoryLimitMax`（10000）。`3.0` は整数として受け付け、`3.5`・NaN・無限大・文字列は受け付けない。値は検証に通ってから代入する）。関数の形にした理由：`Miata.config.history_limit = 100` のようなテーブル代入だと、タイプミスも黙って通ってしまう（`Miata.config` にはメタテーブルが無い）が、関数なら「nil を呼んだ」エラーになり、起動時の設定エラーのダイアログに出る
- **フォーカスの無いペインを移したときのスクロール**：`FileListView::Redraw()` がカーソルの行へスクロールするのは、フォーカスのあるペインだけ。これまでは、フォーカスの無いペインのディレクトリが変わる経路が無かったが、`jump_to(path, pane)` / `history(pane)` が作った。購読の「移動」の分岐（`!reload_memo_`）で、`Redraw()` の後に先頭へスクロールする（`[content_view scrollPoint:NSZeroPoint]`。しないと、前のディレクトリで下までスクロールしていた位置が残る。実測：右のペインを下までスクロールして、左にフォーカスを戻し、`jump_to(別の長いフォルダ, "right")` すると、先頭ではなく途中の行から表示された）
- **`FilterListDialog` の長い行は先頭省略**（`NSLineBreakByTruncatingHead` の段落スタイル）：段落スタイルを付けないと、`drawInRect:withAttributes:` は単語の境目で折り返して1行目だけを見せる（実測：長いパスの末尾=フォルダ名が見えなくなった。日本語は途中で切れた）。収まる行は変わらない
- **一覧から除くのは、移動先のペインの今いるフォルダだけ**：表示用の `List(current)` に、`history_list(pane)` の `pane`（`history` が移す側のペイン）の今のパスを渡す。反対側のペインの今いるフォルダは一覧に残す（先頭に出ることが多い。そこへ移れば、反対側と同じ場所を開ける）。履歴の先頭は、最後に移動したペインの今いる場所なので、そのペインで開くと先頭が除かれる。保存するデータには、今いる場所も含まれる。起動時の場所は記録されない（コンストラクタの `JumpTo(ホーム)` も、前回のペインの場所の復元（`TryRestoreTo`）も）ので、前回の最後の場所が先頭に残っていて、起動直後に履歴を開くと、そこから選べる（復元したペインの今いるフォルダは、一覧から除かれる）

## ペインの状態の保存（いるフォルダ・ソート・フォーカス）

左右のペインのいるフォルダ、それぞれのソート（基準と降順か）、フォーカスしているペインを、終了しても残して、次回の起動で戻す。保存したフォルダに入れなければ（無い・フォルダでなくなった・権限が無い等）、黙って `$HOME` のまま。ユーザー向けの仕様は README の「ウィンドウとペインの状態」。ここには、設計の決定と罠を書く。

- **持ち主は `View`**（`RestorePanes()` / `SavePanesIfChanged()`。`Application` は、`InitializeImpl` の `RestoreHistory` の直後と、`Update()` の最後（`SaveHistoryIfChanged` の隣）で呼ぶだけ）：状態が、モデル（パス: `FileListModel`）とビュー（ソート: `FileListView`、フォーカス: `BrowserView`）に分かれていて、両方を見られるのが `View` だけだから。履歴のように `BrowserModel` には置けない（`SortKey` は `views::FileListView` の入れ子の enum で、models 層から見えない）。ソートをモデルへ移す案は、`Fetch` / `SetSort` / 購読を作り直す大きな変更になるので採らなかった
- **保存先**（NSUserDefaults）：`MiataPaneLeft` / `MiataPaneRight`（辞書: `path`・`sort`・`reverse`）と、`MiataSession`（辞書: `focus` = `left` / `right`）。**ペインごと、フォーカスも別のキー**：片方が動いたときに、もう一方の保存してある値（入れなくて、ホームのままだった場所）を上書きしないため（フォーカスをペインのキーに入れると、ペインを切り替えるたびに両方を書き直す）。辞書にしたのは、`pl_save_string_list` に位置で詰める（`[左のパス, 右のパス, ソート…]`）と、不正な UTF-8 の要素を黙って捨てるので、1 つ抜けると後ろがずれる（右のパスが左に入る）ため。ソートは enum の整数ではなく名前（`name` / `size` / `mtime` / `ext`。Lua の `sort` と同じ）で保存する（`defaults read` で読め、enum の並び替えに強い）
- **`pl_save_string_map` / `pl_load_string_map`**（`platform.h` / `osx.mm`）：文字列から文字列への辞書。空はキーを消す。UTF-8 として不正な名前や値は、その項目だけ捨てる（辞書に nil は入れられない）。読み出しは失敗しない：`dictionaryForKey:` で取り（辞書でなければ nil = 空）、名前・値を `isKindOfClass:` で文字列か検査して、文字列でないものは読み飛ばす（型の検査は読む側。`stringForKey:` は整数を文字列に変換してしまうので、値の取得には使わない）。保存は `setObject:forKey:`（空のときは `removeObjectForKey:`）経由で、テストのスパイが数えるのはこの 2 メソッド
- **復元はビューを作った後、タイマーより前**：パスだけならモデルの段階で戻せるが、ソートとフォーカスはビューが要るので、1 か所にまとめた。`BrowserModel` は、`BrowserView` の構築中に初めて作られる（`FileListModel` のコンストラクタが両ペインを `JumpTo(ホーム)` する）ので、**両ペインは最初からホームにいる**：保存したパスへの移動が失敗しても何も変えなければ、「`$HOME`」は自然に満たされる。ビューは構築中にホームを購読して走査・監視を始めるので、ホームの FSEvents を一度張って捨てることになるが、通常の移動と同じ経路で戻せる
- **復元用の移動は `FileListModel::TryRestoreTo`**（`TryJumpTo` と本体を共有し、履歴に記録しない）：`TryJumpTo` は成功すると履歴に記録する。復元は移動ではないので、履歴の並びを動かさない（上限が注入される前なら記録されない、という偶然に頼らない）。`JumpTo` は使わない：読めないと例外を投げ（コードベースに `catch` は無い）、投げる前に一覧を空にする。`View::JumpToPath` も使わない（失敗でダイアログを出し、履歴から外し、検索バーを触る）。入れなかったときのエラーは捨てる（案内のダイアログを出さない。権限が無いときも同じ：ad-hoc 署名の再ビルドで許可が外れるたびに、起動のたびに出るため。ユーザーの判断）
- **保存の基準は、復元した後の「いまの値」**（`saved_panes_` / `saved_focus_`）で、ディスクの値ではない。ディスクの値にすると、入れなかったペインが、最初のティックでホームを書き込み、保存してあった場所を忘れる。いまの値なら、変わるまで何も書かないので、外付けディスクを外していた起動でも、そのペインを動かすまで保存してある場所は残り、つなぎ直せば戻る。ペインの状態（パスとソートの組）が変わったら、そのペインの組を書き直す（ソートだけ変えても、入れなかった場所は、そのとき上書きされる）。変更の検知は**値の比較**（毎ティック）：`ReactiveProperty::Value()` は同じ値でも毎回通知するので、`ObservePath` の購読では判断できない（再読み込み・自動リロードが同じパスを再通知する）
- **検査は `PaneState`（純ロジック）**：`FromMap` は、パスを `IsPlainAbsolutePath`（絶対パスで、`.` `..` 空の要素と NUL が無い）に合うものだけにし、末尾の `/` を除く（履歴や画面と同じ形）。合わなければ空（復元しない）。`..` を許すと、`NavigateToParent`（字句上の親）が、実際に開いた場所と食い違う。`IsPlainAbsolutePath` は Lua の `jump_to` の入口と共有する（以前は `Application.cc` の static）。`PathHistory::Key` は使わない：改行を弾くが（fzf のため）、ペインの場所には要らない。ソートの名前は `PaneState` が検査しない（意味を知っている `FileListView::ParseSortKey` が調べる）。基準の名前が分からなければ `name` にして、降順の指定は生かす。シンボリックリンクは解決しない（論理パスのまま。履歴や、親へ戻る操作と同じ）
- **`FileListView::ParseSortKey` / `SortKeyName`**：Lua の `sort` と共有する、ソートの基準の名前との変換。`lua_command_sort` は、以前は `std::string` を持ったまま `luaL_error` を呼んでいた（longjmp の規約違反）。今は `std::optional<SortKey>`（デストラクタを持たない）で、引数 2 の型の検査を、基準の名前の検査より先に行う順序は変えていない
- **ソートはペインごと**：Lua の `sort` は、フォーカスのあるペインにだけ効く。保存も 2 ペイン分。ディレクトリの移動・再読み込みで、ソートは保たれる（`Fetch` が `sort_key_` を使う）
- **起動時の限界（未実測）**：(1) 前回のフォルダが、保護された場所（`~/Documents`、`~/Desktop`、`~/Downloads`、外付け、ネットワーク）のとき、`TryRestoreTo` の中（メインスレッド）で OS の許可ダイアログが出て、答えるまで止まる可能性が高い。ad-hoc 署名の再ビルドで許可が外れるので、また出る。(2) 応答しないマウント（切れたネットワークボリューム）は、走査がブロックして、ウィンドウが出る前に起動が固まる。保存した値が残るので、再起動しても再発する。固まり対策（起動中の印、非ローカルの判定、別スレッド + タイムアウト）は入れていない（README に、既知の制約と消し方を書いた）。(3) ターミナル起動（`rake run:*`）と `open` 起動では許可の対象が違うので、同じ保存パスが戻せたり戻せなかったりする
- **戻さないもの**：カーソル位置、マーク、スクロール位置、左右の境界の位置、Quick Look、検索、絞り込み。ソートのダイアログ（`s`）は、今のソートから始まる（`current_sort` で取る。後述「Lua から状況を取る」。以前は、いつも「名前・昇順」から始まった）

## ウィンドウ位置・サイズの保存

`platforms/osx.mm` の `pl_create_main_window()` が、`[g_window center]` の**後**に `setFrameAutosaveName:@"MiataMainWindow"` を呼ぶ。AppKit が、移動・リサイズのたびに `NSUserDefaults`（バンドルIDのドメインの `NSWindow Frame MiataMainWindow`）へ自動で保存し、この呼び出しの時点で、保存済みなら復元する(初回は保存が無いので `center` のまま)。終了時にまとめて保存する処理は無い(強制終了でも最後の状態が残る)。

- **`center` を先に呼ぶこと**：保存済みなら復元で上書きされ、無ければ中央のまま出る。順序を逆にすると、毎回中央に戻る。
- **画面外の保存値**：保存された位置がどの画面にも掛からない場合(モニタを外した後など)は、復元の時点でAppKitが画面内へ寄せる(実測。`-20000, 5000` を保存して復元すると画面内に収まった)ので、自前の補正は要らない。
- **復元はViewを作る前**：`pl_create_main_window()` は `InitializeImpl()` の最初に呼ばれ、`View` はその後にcontentViewのサイズを基準にレイアウトされるので、復元後のサイズで始まる。復元で `windowDidResize:` が呼ばれても、リサイズのハンドラ(`pl_set_resize_handler`)はまだ未設定なので何も起きない。
- **ウィンドウのほかに保存するもの**（どちらも同じ NSUserDefaults で、別のキー）：フォルダの履歴（前述「フォルダの履歴」）と、ペインの状態（後述「ペインの状態の保存」）。左右ペインの境界(`NSSplitView`)の位置は保存しない(`NSSplitView.autosaveName` は、覆い(プレビュー)の位置追従のデリゲートとの相互作用が未確認なので、入れていない)。
