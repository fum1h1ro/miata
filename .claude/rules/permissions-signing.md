## 権限エラーの案内（macOS の保護）

ファイル操作・ディレクトリ移動が「権限が無い」で失敗したとき、エラーに加えて、許可のしかた（システム設定の「フルディスクアクセス」）を案内するダイアログを出す。流れ：失敗 → `FileError`（`FileError.h`。`message` + `permission_denied`）→ **`View::ReportFileError(what, error)`** → `permission_denied` なら `YesNoDialog`（OS の説明 + 案内文 `kPermissionGuide` + 「システム設定を開く」/「閉じる」。既定は「閉じる」）→ 「開く」で `pl_open_full_disk_access_settings()`。権限でない失敗は、通常の `ConfirmDialog`（文面は「what: OSの説明」）。

- **エラーのダイアログを自前で作らず、必ず `View::ReportFileError` に通す**：ゴミ箱（`Application::TrashPaths`。Lua の `trash`）、コピー・移動の失敗（`OnFileOperationCompleted`。始める前の確認の断りも、`StartFileOperation` から）、`make_directory`、`rename_execute`、`reload`、ディレクトリ移動（`View::JumpToOrReport`/`MoveToParentOrReport`）が通している。失敗し得る操作を足したら、ここに通すこと（通さないと、権限の失敗に案内が付かない）。**例外は、起動時のペインの復元（`View::RestorePanes`）**：入れなくても、案内を出さず、黙って `$HOME` のまま（ユーザーの判断。直さないこと）。
- **分類（実測）**：`std::filesystem` の権限の失敗は、`EACCES`（13。書き込めない・読めないディレクトリ）と `EPERM`（1。ロック(`uchg`)されたファイル、OS の保護）で、どちらも `permission_denied`（`FileError::From`）。`pl_trash_file`（`trashItemAtURL:`）は `NSCocoaErrorDomain` の 513（`NSFileWriteNoPermissionError`。下位は `NSOSStatusErrorDomain` の -5000 = `afpAccessDenied`）で、存在しないファイルは Cocoa の 4（権限ではない）。`ToFileError`（`osx.mm`）は、Cocoa の 257/513、下位の POSIX の EPERM/EACCES、OSStatus の -5000 のどれかで権限の失敗とみなす。
- **原因は区別できない**：`EPERM` は、OS の保護（プライバシーとセキュリティ）のほかに、SIP（`/System` など）、ロックされたファイル、App 管理でも返る。`EACCES`（アクセス権）と Cocoa の 513 は、OS の保護とアクセス権を区別できない。案内の文面は「止められた場合は…」と書き、アクセス権が原因のときの確認先（Finder の「情報を見る」）も添えている。SIP やロックの判別（`st_flags`）はしていない（README に、許可しても変更できない場所があると書いた）。
- **`FileErrorSummary`**：複数の失敗（コピー・移動、ゴミ箱）をまとめる。**権限の失敗を、後の別の失敗で隠さない**（`Add` の順序に依らず、権限の失敗があれば、その説明を残す）。件数は全部の失敗。
- **罠：`FileListModel::JumpTo` は、読めないと例外を投げる**（`std::filesystem::filesystem_error`）。コードベースに `catch` が一つも無いので、ユーザー操作の移動に使うと、プロセスが `std::terminate` で終了する（実測: `libc++abi: terminating due to uncaught exception ... Permission denied`。権限を拒否した「書類」フォルダなどに入っただけで落ちる）。ユーザー操作は **`TryJumpTo`/`NavigateToParent`**（失敗しても、パス・一覧・マークに触れず、通知もせず、`FileError` を返す）を使う。`JumpTo` は、起動時（ホーム）とテスト専用。`Reload` も、同じ理由でエラーコード版（`Scan`）。
- **`pl_open_full_disk_access_settings()`**：URL `x-apple.systempreferences:com.apple.preference.security?Privacy_AllFiles`（System Settings もこの形式を解釈する）を `-[NSWorkspace openURL:]` で開き、開けなければ `com.apple.systempreferences`（System Settings.app）そのものを開く。許可を与えるのはユーザーで、アプリからは変えられない。
- **実機で確認できたこと（ユーザーの報告とOSのログ）**：「システム設定を開く」でシステム設定が開き、Miata にフルディスクアクセスを許可できた（macOS 27.0）。許可はシステムの TCC.db に `kTCCServiceSystemPolicyAllFiles | com.fum1h1ro.miata | 許可` として残り、起動し直した Miata は `Allowed (System Set)` と判定された。許可の条件は `cdhash`（実行ファイルのハッシュ）。
- **クラウドストレージ（File Provider。`~/Library/CloudStorage/*` の Dropbox・Google Drive・OneDrive など）の中のゴミ箱は、Finder に Apple Events で頼む（`pl_trash_file` のフォールバック。2026-10-08 に直した）**。以前は未解決で、ユーザーの判断で保留にしていた（2026-10-01）：普段の起動（Dock/Finder/`open`）の Miata から、フルディスクアクセスを許可しても、`trashItemAtURL:` が `Cocoa 513`（権限がない）で失敗した（実測。macOS 27.0、Dropbox。普通のフォルダは問題なし）。OS のログでは、書き込みの瞬間に `kernel (Sandbox) sandboxd rejected approval request from Miata for kTCCServiceFileProviderDomain (<パス>): would require prompt` が出る（Dropbox の許可（`kTCCServiceFileProviderDomain`。システム設定では `full`）が許可済みでも、フルディスクアクセスのオン・オフでも変わらない。読み取り（一覧、`stat`）は `granted by TCC` で通る）
  - **流れ**（`platforms/osx.mm`）：`pl_trash_file` は、まず `trashItemAtURL:`。それが**権限の失敗**（`FileError::permission_denied`）で、かつ `pl_is_in_file_provider_domain(path)` のときだけ、`pl_trash_file_via_finder(path)` の結果を返す（失敗の説明は、Finder に頼んだほう）。呼び出し元（`Application::TrashPaths`。メインスレッドで、1 件ずつ同期）は変えていない。**ターミナルから起動した Miata は、標準の方法が通る**（下の「許可の対象になるアプリ」）ので、Finder には頼まない（初回のダイアログも出ない）
  - **判定 `pl_is_in_file_provider_domain`**：`~/Library/CloudStorage/` の実パス（`realpath`）の**下の、1 つ以上深いフォルダの中身**。`CloudStorage/Dropbox-Personal/x` は true。**`Dropbox-Personal` そのもの（領域）と、`CloudStorage` 直下の項目は false**（領域そのものを Finder に捨てさせない）。**パスの親だけを実パスにする**：`~/Dropbox` のような、領域へのシンボリックリンク経由のパスも領域の中と分かり、path 自身がシンボリックリンクなら、リンクそのものが対象（リンク先ではない）。`CloudStorageX` のような、名前の途中までの一致は、`/` の境目で見て外す。親が実在しなければ false。iCloud Drive（`~/Library/Mobile Documents/`）は対象外（未検証）。テストのために、ホームを引数に取る `IsInFileProviderDomainOf` に分けてある
  - **頼み方 `pl_trash_file_via_finder`**：Apple Event（`core`/`delo`）を `NSAppleEventDescriptor` で組み、対象は `typeFileURL` の記述子（`TrashTargetURL(path).absoluteString` の UTF-8）。**AppleScript の文字列は組まない**（名前の `"` `\` や UTF-8 として不正なバイトで壊れない。テストで確認）。`sendEventWithOptions:` を `WaitForReply | NeverInteract`・20 秒（`kFinderTrashTimeoutSeconds`）で送る。**NeverInteract**：Finder に「すぐに削除しますか」などの確認を出させない（Miata が見えない Finder のダイアログを待ったり、うっかり完全に削除したりするのを避ける。ロックされたファイルは、理由つきの失敗として返る=実測）。**Finder が断ったときは、送信は成功して、返事の `errn`（番号）と `errs`（説明）に入る**ので、それを見る（`errn` が 0 なら成功）
  - **許可の確認は、送信とは別に、先にする**：`AEDeterminePermissionToAutomateTarget(finder, wildcard, wildcard, askUserIfNeeded = true)`（`g_determine_automation_permission`。テストで差し替える）。初回は、「“Miata” が “Finder” を制御しようとしています」のダイアログが出て、**答えるまで返らない**（送信のタイムアウトに、ユーザーが答えるまでの時間を含めないため。拒否は `errAEEventNotPermitted`（-1743）で、ここで分かる）。ダイアログの説明は、Info.plist の `NSAppleEventsUsageDescription`（`cmake/Info.plist.in`。CMake の既定のテンプレートに、このキーを足したもの。`CMakeLists.txt` の `MACOSX_BUNDLE_INFO_PLIST`。Info.plist に新しいキーを足すときは、このテンプレートに足す）。**hardened runtime を付けるなら、`com.apple.security.automation.apple-events` の entitlement が要る**（いまは付けていない）
  - **メインスレッドで呼ぶ**：`AppleEvents.h` には「メインスレッドで呼ぶな（ユーザーの答えを待つので、いくらでも長くなる）」とあるが、`TrashPaths` が同期でゴミ箱を呼ぶので、そのまま呼んでいる。初回のダイアログに答えるまで、Miata 全体が止まる（ダイアログは別のプロセスが出す）。許可済みの呼び出し（50〜100 ms）では、メインのランループは回らない（5 ms のタイマーが 1 回も発火しなかった。試験 `E10`）。**ダイアログを待つ間も回らない**（新しいアプリ ID の初回の許可で、ユーザーが答えるまでの 4.7 秒、5 ms のタイマーが 1 回も発火しなかった。回れば約 900 回。試験 `CONSENT_TIMER`）ので、`Application::Update` が `TrashPaths` の途中に再入することは無い（回ると再入する。`NSTask` の `waitUntilExit` で起きたのと同じ。後述「外部コマンドの起動」）。**別スレッドに任せて、呼んだスレッドをセマフォで待たせる案は、書いたが、実際の Apple Events では確かめられなかった**（確かめようとしたとき、画面がロックされていて、許可のダイアログに答えられず、tccd が止まった）ので、採っていない（上の測定で、要らないと分かった）
  - **失敗の説明 `FinderTrashError`**：-1743 → オートメーションの許可を案内する（「システム設定の「プライバシーとセキュリティ」→「オートメーション」で、Miata の「Finder」をオンにしてください」）、-1712（タイムアウト）→「Finderの応答がありません（ゴミ箱への移動は、続いている可能性があります）」、-600 → Finder が起動していない、それ以外 →「Finderがゴミ箱への移動を断りました (OSStatus N: Finder の説明)」。**`permission_denied` は常に false**：`View::ReportFileError` が付ける、フルディスクアクセスの案内（`kPermissionGuide`）は、この失敗には当てはまらないので、出さない
  - **シンボリックリンクは頼まない**（`lstat`。許可の確認も送信もせず、すぐ失敗にする）：ファイルの URL で頼むと、**Finder の返事が来ない**（実測：絶対パスのファイルへのリンクで、20 秒の上限まで待っても。2 回とも再現。リンクもリンク先も、ゴミ箱へ移っていなかった）。Dropbox などはシンボリックリンクを同期しないので、領域の中には、ふつう無い。Finder のエイリアス（エイリアスファイル）は、通常のファイルとして、普通に移る（リンク先は残る）
  - **Finder に頼んだときの挙動**（ローカルの一時ファイル。試験用アプリ）：ファイル・フォルダ（中身つき）・変わった名前（`"` `\` 空白 日本語 NFD）・エイリアス・読み取り専用（0444）は、ゴミ箱へ移る（許可済みで 50〜100 ms）。ロックされたファイル（`uchg`）→ 失敗（OSStatus -45「ファイルはロックされています」）。存在しないファイル → 失敗（-10010）。**本物の Dropbox では、この実装（`typeFileURL` の記述子で頼む）で、ファイル 1 つが通った**（2026-10-09、ユーザーの実機。署名した Miata を `open` で起動 → 初回にダイアログ → 許可 → ゴミ箱へ移る → Finder のゴミ箱の「元に戻す」で戻せる → 再度削除してもダイアログは出ない）。それ以前の Dropbox の試験は、`NSAppleScript` の `delete`（alias で渡した）の、空のファイル 1 つ。フォルダ・複数・大きなファイルは未確認
  - **何が拒否されていたか（試験用の小さな GUI アプリ `SigProbe` での切り分け。2026-10-08。LaunchServices 起動・アドホック署名・アプリ ID は試験ごとに別）**：(1) 拒否されるのは**ゴミ箱への移動だけ**。ファイルプロバイダの許可（新しいアプリ ID では、フォルダを最初に読んだときに、システムのダイアログが出て、答えるまで読み取りも止まる）を済ませたアプリは、ファイルの作成・リネーム・`unlink` が、アドホック署名でも通る（フォルダの作成・コピー・移動は未試験）。(2) ゴミ箱は、`trashItemAtURL:` も `NSWorkspace recycleURLs:completionHandler:` も、**同じように拒否**された（Cocoa 513。`sandboxd rejected approval request … would require prompt` が、`tccd` が許可と答えた約 10 ms 後に出る）。(3) 許可のダイアログに答えても、新しいプロセスでも、新しいアプリ ID の最初の書き込みでも、直らない（最初の失敗が記憶されている、という話でもない）。(4) 署名（下の「署名で直らなかったこと」）でも直らない。**Developer ID・hardened runtime・公証は、試していない**（拒否が、これらで変わるかは未検証。ターミナル（WezTerm=Developer ID・公証済み）から起動した Miata は通り、チーム ID 付きで署名してフルディスクアクセスを結び付けた Miata は通らなかった、という食い違いは、説明できていない）。(5) **Finder に Apple Events で削除を頼むと通った**（アドホック署名・チーム ID なしの試験用アプリで、ファイルは Dropbox-Personal から `~/.Trash` へ移った。初回は「Finder を制御」のダイアログ）
  - **差は「許可の対象になるアプリ（responsible process）」**（実測、同じ実行ファイル・同じ署名で比較）：Miata を**ターミナル（WezTerm）から直接起動**すると、アプリ自身のプロセスの中の `trashItemAtURL:` が**成功**する（`sandboxd` が確認するのは、起動元 WezTerm のフルディスクアクセスだけで、Dropbox 側の確認は発生しない）。普段の起動（LaunchServices。起動元は Miata 自身）だと、フルディスクアクセスの確認は `Allowed` なのに、**Dropbox 側の確認が先に出て「プロンプトが要る」として拒否**される。
  - **効かなかったこと**：(1) **別プロセスに任せる**（Miata が `/usr/bin/trash` を子として起動する実装を作ったが、**外した**）：普段の起動の Miata の子の `trash` も、同じ Dropbox 側の確認で拒否された（親が先に書き込みを試みていないまっさらな状態でも。承認の問い合わせは `from trash` として出る）。ターミナルから起動した `trash` が通るのは、起動元がターミナルだから。(2) Info.plist に `NSFileProviderDomainUsageDescription` などの**用途説明**を足す（`.app` のコピーで確認。実行ファイルの `cdhash` は変わらない）：変わらない。(3) Dropbox の許可の付け外し（`tccutil reset`、システム設定のスイッチ）、フルディスクアクセスのオン・オフ：変わらない。
  - **オートメーションの許可の持ち方**（試験用アプリでの実測。Miata 本体では未確認）：アドホック ↔ 証明書の署名の切り替えと、中身を変えたビルド（4 通り）のすべてで、`AEDeterminePermissionToAutomateTarget(…, false)`（ダイアログを出さない確認）が「許可済み」を返した。**フルディスクアクセスが「アプリ ID + コード要件」に厳密に結び付く（下の「TCC の許可は…」）のと違う**。新しいアプリ ID では `-1744`（`errAEEventWouldRequireUserConsent` =決まっていない=ダイアログが要る）になる。ユーザーの TCC.db は私の端末から読めなかったので、行の中身（`csreq`）は見ていない
  - **罠：答えられていない許可のダイアログがあると、ほかの Apple Events の許可の確認も止まる**（実測：試験用アプリのダイアログに誰も答えず、アプリが時間切れで終了したあとも、ダイアログが画面に残り、別の試験用アプリの `AEDeterminePermissionToAutomateTarget(…, false)`（ダイアログを出さない確認）まで、4 分間返らなかった。ユーザーが席を外して、画面がロックされていた）。ダイアログに答えるか閉じると、続きが動く。**試験の作法**：ダイアログが出る試験は、ユーザーがそこにいるときだけ行う（出す前に、通知を送る）。画面の窓の一覧（`CGWindowListCopyWindowInfo`。画面は撮らない）で、`UserNotificationCenter`（許可のダイアログ）と、`SecurityAgent` + 全画面の `loginwindow`（ロック画面）があるかが分かる。試験用アプリには、固まっても終わる見張り（`_exit` を呼ぶ別スレッド）を付ける
  - **本物の Miata の権限で、画面を出さずに試す方法（スクラッチで使った）**：試したい処理を入れた dylib を、`DYLD_INSERT_LIBRARIES` で Miata に読み込ませ、コンストラクタ（`main` より前）で実行して結果をファイルに書き、`_exit(0)` する。起動は `open -n -g -W --env DYLD_INSERT_LIBRARIES=... --env 名前=値 Miata.app`（LaunchServices 経由。普段の起動と同じ）、または実行ファイルを直接起動（起動元がターミナルになる）。Miata の実行ファイルは ad-hoc で hardened runtime ではないので、DYLD の環境変数が効く。ウィンドウもキー入力も発生しない。**危ない操作は、試験用に作った空のファイル（名前と大きさで確かめる）にだけ向けること。**
- **罠：許可の対象（responsible process）**：`rake run:*` は、実行ファイル（`Miata.app/Contents/MacOS/Miata`）を、ターミナルから**直接**起動する（`open` を経由しない）。このように起動したプロセスの TCC・サンドボックスの判定は、起動元のアプリ（ターミナル）のものとして行われる（実測：直接起動した Miata の書き込みでは、承認の問い合わせの `Resp:` がターミナル（WezTerm）で、そのフルディスクアクセスで通った）。ターミナルに許可が無いとき、Miata を許可しても効かないか（ターミナルに許可が要るか）は未確認。Miata 自身の許可を試すときは、`open _build/debug/Miata.app` で起動する（Dock/Finder 起動と同じ）。README に書いた。
- **署名（`Rakefile` の `sign_app`。環境変数 `MIATA_CODESIGN_IDENTITY` があるときだけ）**：`make` のあとに、毎回、`codesign --force --sign <identity> --timestamp=none` で `.app`（バンドル）に署名して、`codesign --verify --strict` で確かめる。毎回署名し直すのは、`make` が、リソース（`resources/` の Lua など）だけをコピーし直したときも、署名が古くならないようにするため（実測: リソースだけを変えたビルドも、署名が通って、許可が残った）。コマンドは `verbose: false` で、証明書の文字列を出力に出さない。hardened runtime は付けない（テストの `DYLD_INSERT_LIBRARIES` が効かなくなる。配布用の Developer ID・公証は、まだ組み込んでいない）。`make` / Xcode を直接使うと、署名されない。環境変数が無いときは、これまでどおり、リンカーのアドホック署名（`adhoc,linker-signed`・チーム ID なし）のまま
- **TCC の許可は、「アプリ ID + コード要件」の組に結び付く（検証済み。macOS 27.0）**：システムの TCC.db（`/Library/Application Support/com.apple.TCC/TCC.db`。`/usr/bin/sqlite3 -readonly` で読める）の行は、`client`（バンドル ID）と `csreq`（コード要件）を持つ。アドホック署名のアプリは、要件が `cdhash H"…"`（実行ファイルのハッシュ）なので、ビルドし直すと別物になる。証明書で署名したアプリは、要件が `identifier "com.fum1h1ro.miata" and anchor apple generic and certificate leaf[subject.CN] = "Apple Development: …" and certificate 1[field.1.2.840.113635.100.6.2.1] exists` になり、同じ証明書で署名し直せば、ハッシュが変わっても合う。**実測**：署名したビルド（ソースを 1 行変えて、本当にビルドし直したもの・リソースだけ変えたもの）が、フルディスクアクセスで保護された場所（システムの TCC.db）を `open(2)` できた。記録も書き換わらない。要件は `xxd -r -p` と `csreq -r- -t` で読める（`SELECT hex(csreq) …`）
- **罠：要件に合わないビルドが要求すると、`tccd` が記録を拒否に書き換える**：同じバンドル ID のプロセスが `kTCCServiceSystemPolicyAllFiles` を要求して、行の `csreq` に合わないと、`tccd` は `Denied (Service Policy)`（`DB Action:Update, UpdateVerifierData`）と答えて、**行を書き換える**（`auth_value` 0・`auth_reason` 5・`csreq` は要求した側のものに）。ビルドし直したアドホックの Miata が許可を失う症状の、仕組みはこれ（2026-10-08 の 14:16 に、許可が「拒否」になっていたのも、おそらく）。署名の違うビルドを動かしただけで、署名したほうの許可が消える。**試験・運用の作法**：署名の違う（同じバンドル ID の）ビルドを、続けて動かさない。確かめたい署名のものを先に動かし、アドホックの対照は最後にするか、別のバンドル ID にする。毎回の前に、行（`auth_value` と、読み出した `csreq`）を読み直す。**システム設定で、一覧の既存の Miata をオンにするだけでは、`csreq` は古いまま**（署名を切り替えたあとは、「－」で外して、新しいアプリを追加し直す。追加したあとに、`csreq` が署名の要件になったかを読んで確かめる）。許可は、バンドル ID + 要件の組に結び付く（パスではない）ので、同じ署名のアプリなら、場所が違っても効く
- **署名で直らなかったこと：クラウドストレージ（Dropbox-Personal）のゴミ箱（2026-10-08 に検証）**：普段の起動（`open`。LaunchServices）で、同じ Miata を、署名だけ変えて試した（`DYLD_INSERT_LIBRARIES` の dylib で、`main` の前に `trashItemAtURL:` を 1 回だけ。試験用の空のファイル `miata_probe_…` を、`Dropbox-Personal` の直下に作って、すぐ消す）。**アドホック（対照）・チーム ID のある Apple Development 署名・同じ署名＋フルディスクアクセスを署名の要件に結び付けた状態の 3 つとも、`trashItemAtURL:` が Cocoa 513 で失敗**し、ログは `kernel (Sandbox) sandboxd rejected approval request from Miata for kTCCServiceFileProviderDomain (…): would require prompt`。**`tccd` に `FileProviderDomain` の問い合わせが出ないまま、`sandboxd` の中で決まる**（ダイアログも出ない）。なお、`access(W_OK)` は、アドホックでも成功する（`tccd` は `FileProviderDomain` を許可と答える）ので、この失敗の再現には使えない（実際の書き込みが要る）。未検証：Developer ID 署名、hardened runtime、公証。（作成・リネーム・削除が通ること、Finder への Apple Events が通ることは、その後に確かめた=上の「クラウドストレージの中のゴミ箱」の項目）。**検証の作法**：署名ありのコピーは、`cp -R _build/debug/Miata.app` して `codesign --force --sign <identity> --timestamp=none`（hardened runtime が無いので、dylib の注入が効く）。Dropbox に触る試験は、**会社の Dropbox（`~/Library/CloudStorage/Dropbox-…` のうち、会社のもの）には、触らない**。個人の Dropbox の直下に、試験用の空のファイルを 1 つ作って、すぐ消す形にして、そのたびに、ユーザーの許可を取る。**後片付けは、その回に作ったファイルの名前だけを消す**（`miata_probe_*` のようなワイルドカードで、ごみ箱を掃除しない。以前の試験の残りを、巻き込んで消した）
- **証明書（2026-10-08）**：個人の有料チーム（Individual）で、Apple Development（有効期限 1 年）と Developer ID Application を作った。**Developer ID は、旧い中間 CA（G1）で発行され、有効期限が 2027-02-01 に頭打ち**（会社のものは G2 で 2030 年まで）。配布に使うなら、期限前に、G2 で作り直す。会社のチームの証明書（Apple Development・Developer ID Application・Apple Distribution）は、個人のアプリには使わない（ユーザーの判断なしに使わない）

## アプリアイコン

**元画像は `assets/AppIcon.png`（1024×1024 の正方形の PNG）、変換後が `resources/AppIcon.icns`**。`rake icon`（`Rakefile` の `icon` タスク）が、前者から後者を作る。**両方をコミットする**：`.icns` はビルドに必要で（CMake は `.icns` を作らない）、元画像は次に直すときに必要。元画像を直したら `rake icon` で `.icns` も作り直して、一緒にコミットする（今コミットしてある `.icns` は、`assets/AppIcon.png` から `rake icon` を実行すると、バイト単位で同一のものができる）。

- **元画像を `resources/` に置かない理由**：`CMakeLists.txt` の `file(GLOB_RECURSE RESOURCES "resources/*")` が、`resources/` の全ファイルを `MACOSX_PACKAGE_LOCATION Resources`（= `Contents/Resources/` 直下に平らにコピー）で `.app` に入れるため。1024px の PNG が `.app` に同梱されてしまう。`assets/` は CMake が見ないので入らない。
- **`Info.plist` への登録**：`set_target_properties(app PROPERTIES MACOSX_BUNDLE_ICON_FILE "AppIcon")`（拡張子なしの `AppIcon`）。`resources/AppIcon.icns` は、他の `resources/` のファイルと同じ経路で `.app` に入る。 `Info.plist` そのものは、`cmake/Info.plist.in`（CMake の既定のテンプレートに、`NSAppleEventsUsageDescription` を足したもの）から作る（`MACOSX_BUNDLE_INFO_PLIST`。後述「権限エラーの案内」）。
- **`rake icon` の変換元は固定**（`ICON_SOURCE`）で、引数を取らない。以前の `rake 'icon[x.png]'` の形で呼ばれたときに、引数を黙って無視すると、x.png を変換したつもりで別の画像から `.icns` ができてしまうので、`args.extras` が空でなければエラーにする（引数を宣言すると `rake -T` に擬似的な引数名が出てしまうので、宣言していない）。元画像が無い/正方形でない/画像として読めない場合は、書き込む前にエラーで止まる（既存の `.icns` は壊れない）。`sips` で10サイズ（16〜1024 とその `@2x`）の `.iconset` を作り、`iconutil -c icns` で `.icns` を作る。
- **新しい `resources/` のファイルは cmake の再生成が要る**：`GLOB_RECURSE` は構成時にしか評価されない。`rake build:debug`/`build:release` は cmake を再生成するので、ふつうは気にしなくてよい。直接 `make` するときだけ注意。
- **macOS のアイコンの作法**：角丸の形と余白（1024 の枠に 824 の角丸四角）は画像の側に含める。システムは形を整えない。
- **確認のしかた**：`NSWorkspace iconForFile:` に `.app` のパスを渡すと、システムが返すアイコンが分かる（ビルドしたバンドルで、仮のアイコンが返ることを確認済み）。Dock/Finder のキャッシュで古い絵が残る場合は、この方法で `.app` 側が正しいかを切り分けられる。
