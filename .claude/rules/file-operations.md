# ファイル操作（コピー・移動）と進捗パネル

> 機能別の設計メモ。上の `paths:` のファイルを触ると自動で読み込まれる。`Application.cc` など複数の機能が同居するファイルでは載らないので、そのときは CLAUDE.md の「設計メモの索引」から、該当するファイルを自分で読むこと。
> テスト・実測・実機未確認の記録は `.claude/notes/file-operations.md`（自動では読み込まれない。テストを書く・直す・検証するときに読む）。

## ファイル操作（コピー・移動）

`Miata.command.copy_to()` / `move_to()` → `Application::StartTransfer`（`Application.cc`。始める前の確認は `CheckTransfer`）→ `FileOperationManager::Start(type, sources, dest_dir, overwrite)`（`FileOperation.h/.cc`）→ 裏スレッドの `Run`。完了は、毎ティックの `FileOperationManager::Update()` が拾って、メインスレッドでコールバック（`Application::OnFileOperationCompleted`）を呼ぶ。そこで、進捗パネルへの完了の通知（`View::FinishProgress`）・一覧の再スキャン・マークの解除・失敗の通知（`View::ReportFileError`）をする。**どのペインを更新するかは、パスで引く**（`View::ReloadDirectory(dest_dir)` と、`sources` の親フォルダごとの `ReloadDirectory`（移動）/ `UnmarkPathsIn`（コピー）。いま、そのフォルダを表示しているペインだけ。左右が同じなら両方）：対象と宛先は、Lua から渡された任意のパスで、バックグラウンド実行中に、ペインが別のフォルダへ移ることもあるため。以前は、開始時にペインのモデルへのポインタ（`src_model` / `dest_model`）と `src_dir` を持ち回って、完了時にパスを比べていたが、`FileOperationCompleted` から外した（`FileOperationManager` は、`dest_dir` と `sources` だけを知る。裏スレッドは、ペインにもモデルにも触れない）。**成功したときのダイアログ（以前は「完了しました」）は出さない**：進捗パネルが「完了」を見せる。上書きかスキップかは、スレッドを始める前に、操作全体で 1 つ決まる（`bool overwrite`。実行中に画面の返事は待たない）。確認ダイアログ（上書きか）は C++ には無い：Lua（`resources/test.lua` の `c` / `m`）が、`check_transfer` で同名を知って、`dialog_yes_no` で聞き、`copy_to` / `move_to` の `opts.overwrite` で渡す（後述 `lua-commands.md`「ファイルの操作（部品と組み立て）」）。ゴミ箱（Lua の `trash` → `Application::TrashPaths`）はメインスレッドで同期、他アプリへのドラッグ（`BeginDrag`）は相手が処理するので、どちらもここを通らない。

### 始める前に断る（`FileOperationGuard`）

- **断る組み合わせ**（どれも、そのまま進めると、ファイルを失う・コピーが増え続ける。1〜3 は、2026-10-06 に、スクラッチの一時フォルダで再現した。4・5 は、Lua から任意のパスを渡せるようになって（2026-10-10）足した）：
  1. **先が元と同じ実体**（同じフォルダへの操作。起動直後は左右とも `$HOME` なので、起こりやすい）。Move の「上書き」が、`Run` の `remove_all(dst)`（dst == src）で、元のファイル・フォルダを、中身ごと**完全に消した**（ゴミ箱に入らず、結果は「失敗」と表示された）。Copy は、（以前の `std::filesystem::copy` では）同一ファイルを検出して失敗にするだけだった（`Function not implemented`）。いまのコピーは、ガードが先に断る
  2. **先のフォルダが、元のフォルダの中**（またはそのもの）。Copy が、`File name too long` で止まるまで、入れ子に増殖し続けた（小さなテスト用ツリーで 670 個。大きなフォルダなら、ディスクを埋めうる）。Move は OS が拒否する
  3. **Move だけ**：先の同名のフォルダが、元の祖先（`/a/b/b` を `/a` へ。先 = `/a/b` が元の親）。「上書き」が `/a/b` を丸ごと消し、**移すフォルダごと、無関係な兄弟のファイル（`/a/b/other.txt`）まで失う**。Copy は、フォルダへ重ねるだけで壊さないので、断らない
  4. **対象の中に、先で同じ名前になるものがある**（`FindDuplicateName`。別々のフォルダの同名のファイルなど）。以前は、対象が、いつも 1 つのフォルダ（開いているペイン）の中だったので、起きなかった。コピーの上書きでは、2 つ目が 1 つ目を置き換え、スキップでは黙って落ち、**移動の上書きでは、先に移した 1 つ目が、ゴミ箱にも入らずに消える**。名前は `pl_name_collation_key`（NFC + 小文字）で比べる：大文字小文字・正規化を区別しないボリューム（APFS の既定）では、`a.txt` と `A.TXT`、NFC と NFD の `é` が、先で同じ名前になる（区別するボリュームでは、別の名前でも断る=安全側）。開始前（`CheckTransfer`。重なっている 2 つ目の名前を理由に出す）と、`Run`（項目ごとに、先に置いた名前の集合と比べて、2 つ目以降を失敗にする。前の項目は進む。多重の防御）の両方。「先に元からある同名」（上書きの確認の元）とは別の話
  5. **対象の最後が、名前ではない**（ルート・`.`・`..`）と、**末尾に `/` のあるパス**：先は `dest_dir / 元.filename()` で決まるので、`filename()` が空（`/a/b/`）や `.` だと、先が `dest_dir` そのものになり、**移動の「上書き」が、`dest_dir` を丸ごと消す**。末尾の `/` は落として（`WithoutTrailingSlash`）、同じ名前のものとして扱い、名前の無いものは断る（`HasTransferName`）
- **比べるのは実体（`st_dev` と `st_ino`）**で、パスの文字列ではない。接頭辞の比較は、`foo` と `foobar` を取り違え、シンボリックリンクや、大文字小文字を区別しないボリューム（APFS の既定）の別の綴りを見逃す。`ChainOf` が、`weakly_canonical` でリンクを解決したパスの、自分とルートまでの祖先の実体の列を作る。(2) は「元の実体が、先の列にあるか」、(3) は「先の同名の実体が、元の親の列にあるか」で判定する。**`st_dev` も比べる**：ボリュームのルートの inode は、どのボリュームでも 2 なので、`st_ino` だけだと、別のボリューム全体を通常のフォルダへコピーするのを、「先の祖先 `/` が元」と取り違えて断る（ディスクイメージで確かめた）
- **元はリンクそのもの（`lstat`）を見る**。リンク先は見ない。以前の `Run` は `std::filesystem::copy` で、リンクをたどって中身をコピーしたので、**フォルダへのリンクを、そのリンク先の中へコピーする**と、(2) に当たらずに増殖した（再現済み: `File name too long` で止まるまで）。いまのコピーは、リンクをリンクのまま写す（後述「コピーの中身」）ので、この穴は無い（リンクそのものを 1 つ置くだけ。テスト `symlink_into_target`）
- **開始前（`CheckTransfer`。`StartTransfer` と Lua の `check_transfer` が使う）と、`Run` の直前の、両方で確認する**（同じ `FileOperationGuard`）。`Run` の確認は、確認してから項目の順番が来るまでに、状況が変わっていたときの多重の防御。断る理由は `FileError` にして、開始前は `ReportFileError`（「コピーできませんでした (名前): 理由」）、`Run` は失敗として数える。**開始前は、上書きの確認より前**（どちらを選んでも進められないので、答えさせない）：`check_transfer`（画面に触らない。`false, 理由の文` か `true, 同名の宛先の配列`）を、Lua が先に呼び、断られたら理由を `dialog_confirm` で知らせて終わる。同名があるときだけ、上書きかを聞く。`copy_to` / `move_to` は、始めるときに、同じ `CheckTransfer` をやり直す（`check_transfer` を呼ばずに呼ばれても、ファイルは失われない。こちらは、断る理由を `ReportFileError` でダイアログにする）。**宛先が存在するフォルダでなければ、どの項目も置けないので、断る**（`CheckTransfer` の先頭。理由は「コピー先が、存在するフォルダではありません」。名前は付かない）。複数の対象のうち、どれかが断られたら、全体を断る（最初に断られた 1 つの名前を出す。並びは、渡された順。既定の `c` / `m` では、画面の順で、フォルダが先）
- **調べられなかったとき（`unknown`）**：元か先の場所を `stat` できない（元が外部で消えた、権限が無い）。**開始前は断らない**（操作を始めて、項目の失敗として知らせる）。**`Run` は、Move の「上書き」で先を消す直前だけ、`unknown` なら消さずに失敗にする**（元が消えているのに、先だけ消す、を防ぐ）。親の祖先の列だけが調べられない状況は、元の `lstat` が通れば作れない（到達しない防御。変異テストで生き残る）

### コピーの中身（自前の再帰 + `copyfile(3)`）

`FileOperationManager::Run` の Copy と、Move の別ボリューム（`rename` が `EXDEV` のとき）の「コピーしてから消す」が、`CopyEntry`（`FileOperation.cc` の無名名前空間）を呼ぶ。ユーザー向けの仕様は README の「ファイル操作」。**ユーザーの決定: コピーは Finder 並み**（更新日時・拡張属性を引き継ぎ、APFS ではクローン。リンクはリンクのまま）。以前は `std::filesystem::copy(src, dst, recursive | skip_existing か overwrite_existing)`：中身だけ（`COPYFILE_DATA` 相当。更新日時は、コピーした時刻。拡張属性は落ちる）、リンクはたどる（壊れたリンクで止まる。フォルダへのリンクは中身ごと写す=増殖）、フォルダは、元の権限で作るので、読み取り専用のフォルダだと中身を置けない、だった。

- **構成**：`CopyEntry`（1 項目。`lstat` で種類を見て振り分ける）→ フォルダなら `CopyDirectory`（作る/重ねる・子を 1 つずつ `CopyEntry`・最後に属性）、ファイルとリンクなら、先に同名があるときの扱い（`OnConflict`: `Skip` / `Overwrite` / `Fail`）に従って、`pl_copy_file`（`copyfile` を 1 回）。移動は `MoveEntry`（同じボリュームなら `rename`、別のボリュームなら `CopyEntry` + 元の削除）。OS 依存は `platform.h` の `pl_copy_file(src, dst, replace, on_progress)` と `pl_copy_directory_attributes(src, dst)`（`osx.mm`。どちらも `std::error_code` で返す）。**`COPYFILE_RECURSIVE` は使わない**：既存の先のフォルダにマージせず、入れ子にする（`dst/tree/tree/…`。実測）うえ、リンクをたどる。ファイルごとに `copyfile` を呼ぶ自前の再帰なら、マージ・スキップ・上書き・リンク・失敗の扱いを、こちらで決められる
- **フラグ**（`pl_copy_file`）：`COPYFILE_ALL`（中身・更新日時・権限・拡張属性・ACL。ナノ秒の更新日時まで引き継ぐ。別のボリュームでも）`| COPYFILE_NOFOLLOW_SRC`（元がリンクなら、リンクそのものを写す。相対・絶対・壊れたリンク・フォルダへのリンクのすべて、リンク先の文字列のまま）`| COPYFILE_CLONE`（APFS の同じボリュームではクローン。256 MiB で 7 ms、コールバックは 0 回。別のボリューム・APFS 以外では、普通のコピーに戻る。**クローンは容量を共有する**ので、コピー後もディスクの空きがほとんど減らない。確かめるには `fcntl(F_LOG2PHYS)` の物理位置が元と一致するかを見る）`| COPYFILE_EXCL`（先に同名があれば `EEXIST`。壊れたリンクの先も）。`CopyEntry` は、`Skip` のときの `EEXIST` を**スキップ（エラーではない）**として扱う（先に調べてから置くまでの間に、同名ができた場合も同じになる）。**置き換え（`replace`）は、`COPYFILE_UNLINK` を使わない**：`UNLINK`（先を消してから置く）は、置く途中で失敗すると、先だけが失われる。**クローンのときは、元を調べる前に先を消す**（実測 2026-10-07: 元が `0000` で読めないだけで、先が消えた。`CLONE` を外すと残る）。容量が足りないときも同じ。代わりに、**同じフォルダの一時ファイル（`.miata-copy-<pid>-<連番>-<試行>`）へ `EXCL` でコピーして、全部成功したときだけ `rename` で付け替える**。失敗したときは、一時ファイルを消して（`copyfile` も消す。念のため `unlink`）、先は無傷。`rename` は、先がリンクならリンクそのものを置き換え（リンク先は無傷）、別のハードリンクの中身は変えず、読み取り専用の先（`0444`）も置き換え、**先がフォルダなら `EISDIR` で失敗する**（`UNLINK` は、空のフォルダを消して、ファイルを置いてしまった。実測）。一時ファイルの名前は、先の名前を使わない（名前の長さの上限を超えないため）。同じ名前が既にあれば（前の異常終了の残りなど）、`EXCL` が `EEXIST` にするので、消さずに、次の番号でやり直す（8 回まで）。**一時ファイルは、コピーの間、先のフォルダの一覧に見える**（「.」で始まる名前でも、一覧は隠さない。終わると、名前が付け替わって消える。異常終了すると残ることがある）
- **`pl_copy_file` に渡してよいのは、通常のファイルとリンクだけ**（呼ぶ側 `CopyEntry` が先に振り分ける）。実測：(1) **フォルダを渡すと、中身を写さずに、空のフォルダを作る**（`CLONE` でも）。(2) **デバイスを渡すと、読み出して、普通のファイルにしてしまう**（`/dev/null` で、サイズ 0 の普通のファイルができた。`/dev/zero` のようなものなら、読み続けると考えられる=未実測）。FIFO は `ENOTSUP`。だから、`S_ISREG` でも `S_ISLNK` でもない元（FIFO・ソケット・デバイス）は、`CopyEntry` が `ENOTSUP` で断る。(3) 元がファイルで先が同名のフォルダのときは、`CopyEntry` が、ファイルを置く前に、`EISDIR` で断る（置き換えの `rename` も、フォルダには `EISDIR` で失敗するが、一時ファイルを作ってから失敗するより、先に断る）
- **フォルダ**（`CopyDirectory`）：**`0700` で作り**（元が `0555` でも、中身を置けるように）、子を 1 つずつ置いてから、**最後に** `pl_copy_directory_attributes`（`COPYFILE_METADATA` = 権限・更新日時・BSD フラグ・拡張属性・ACL。実測: 隠しフラグ・拡張属性・`0555`・更新日時が写る）を呼ぶ。属性は最後でないといけない：更新日時は子を足すたびに書き換わり、読み取り専用の権限だと中身を置けなくなる。**中身が失敗して止まったときも、属性は写す**（作りかけのフォルダに、`0700` と今の時刻が残らない）。**既にあったフォルダ（重ねるとき）の属性は触らない**。`pl_copy_directory_attributes` は、先が無いと、フォルダを作ってしまう（実測。契約は「先は存在するフォルダ」）
- **種類の食い違い**（同名のファイルとフォルダ）：どちらも消さず、エラー（フォルダ → 同名のファイル/リンクは `ENOTDIR`、ファイル/リンク → 同名のフォルダは `EISDIR`）。`std::filesystem::copy` は、ファイルを同名のフォルダの**中へ**入れ（`dst/name/name`）、空のフォルダを同名のファイルへは、黙って成功していた：意図して変えた（テスト `differential` は、名前で種類を固定して、この違いを除く）。**先がリンクのときは、リンクを通らない**（`lstat`。フォルダへのリンクは、「フォルダ」と見ない。以前は、リンク先へ重ねた）
- **リンクは、リンクのままコピーする**：ツリーの中のリンクは、たどらない（循環するリンクも、フォルダへのリンクを中身ごと写すことも無い）。トップレベルの項目がリンクでも同じ（リンクそのものをコピー）。先に同名のファイルがあれば、`overwrite` のときだけリンクに置き換わる。**以前の既知の穴（フォルダへのリンクを、そのリンク先の中へコピーすると増殖する）は、これで消えた**
- **同名があるかは、リンクそのもので調べる**（`lstat` / `symlink_status`）：`CopyEntry` のすべてと、`Application::CheckTransfer` の同名の数え上げ（上書きの確認を出すかの元）と、Move の「先が既にあるか」。Lua の `exists(path)` と、`rename_to` の「先に何かあれば断る」も、同じ見方（`ExistsNoFollow`）。後ろの 2 つは、同じ `ExistsNoFollow`（`FileOperation.h`）を使うので、見方は構造でそろう。以前は `std::filesystem::exists`（リンクをたどる）で、**壊れたシンボリックリンクが同名だと、「無い」と見て**、確認が出ないまま、コピーが黙ってスキップした（新しい `CopyEntry` は、リンクを同名として扱うため、合わせないと、この食い違いが出る）。テスト `dangling_dst`（コピー・移動・別のボリューム。スキップ／上書き）、`conflict_dangling_link`（アプリ全体: 確認が出る）
- **作ったばかりのフォルダの中で、同名が既にあれば、衝突として失敗にする**（`CopyEntry` の `OnConflict::Fail`。`CopyDirectory` が、自分で作ったフォルダ（`dst_exists` が false）の子に渡す。別のボリュームへの移動のコピー（`MoveEntry`）も、トップレベルで渡す。`Fail` のときは `pl_copy_file` を `replace = false`（`EXCL`）で呼ぶので、調べてから置くまでの間に、ほかが同名を作っても、置き換えない）：そこにある同名は、この操作で先に置いたものか、ほかが作ったもの。大文字小文字を区別するボリューム（Case-sensitive APFS）から、区別しないボリュームへ、`A.txt` と `a.txt` を持つツリーをコピー・移動すると、2 つ目が 1 つ目と同じ名前になる。以前（`std::filesystem::copy` の `skip_existing`）と、スキップを成功に数える作りでは、**移動が、置かれなかった `a.txt` の元を、`remove_all(src)` で消してしまう**（上書きなら、先に置いた `A.txt` が消える）。失敗にすれば、移動は元を消さない。重ねる（既にあったフォルダの中の）同名は、これまでどおりスキップ・上書き（衝突に数えない）。テスト `case_collision`（ディスクイメージを `-fs "Case-sensitive APFS"` で作る。ファイル・フォルダの衝突、移動・コピー、上書きの有無）。正規化の違いだけの名前（NFC と NFD）の衝突は、確かめていない
- **最初のエラーで止める**（1 つの項目の中。`CopyDirectory` のループが、エラーを `result` に持って抜ける）。それまでに置いたものは残る。ほかの項目（マークが複数のとき）は続ける。失敗は項目ごとに 1 件で、`FileErrorSummary` に入る（権限の失敗は、案内の対象。テスト `unreadable`）
- **Move の別ボリューム**：`rename` が `EXDEV` → `CopyEntry` が成功したときだけ `remove_all(src)`（失敗したら、元は消さない。テスト `cross_volume_failure`）。リンクは、リンクのまま移る（以前は、リンク先の中身のコピーに変わった）。**既知の制約（以前から）**：読み取り専用のフォルダ（`0555` など）を含むツリーは、コピーはできるが、`remove_all` が中身を消せず、失敗として知らせる（先には全部ある。元は一部が残る。データは失わない）。テスト `cross_volume_readonly_dir` が、この現状を記録している（直したら、期待を変える）。**もう 1 つの既知の制約（以前から。コードレビューで指摘）**：Move の「上書き」（`MoveEntry`）は、先を `remove_all` してから `rename`（別のボリュームなら、続けてコピー）するので、`rename`・コピーが失敗すると（元の親が書き込めない・元が読めない・容量が足りない・元が `uchg`）、先だけが失われる。コピーの置き換えは、上のとおり、一時ファイル + `rename` で守っている。移動は、フォルダの上書きが「丸ごと置き換え」なので、同じ作りにしていない（先を一時名へ退避して、成功したら消す・失敗したら戻す、という作りにすれば守れる。未実装）
- **速度**：5000 個の小さなファイルで、自前の再帰 0.58 秒 / `std::filesystem::copy` 0.64 秒（同じツリー）。2 万個 × 4 KiB の実測（スクラッチ）は、`ALL|CLONE` 2.39 秒 / `std::filesystem::copy` 2.73 秒（`ALL` だけだと 4.96 秒。`CLONE` が効く）。**フォルダごとのクローン（`copyfile` の `CLONE` を、フォルダに対して使う）は、使っていない**：`copyfile` はフォルダを渡すと、中身を写さない（上記）。同じボリュームのフォルダを一瞬でコピーする最適化は、できていない
- **errno の退避**：`CopyFileWithFlags` は、`copyfile_state_free` の前に errno を控える（free が errno を書き換えることがあるので）。入れ替える変異は、検出できなかった（実際に書き換わるかは、未確認の防御）。`copyfile` が -1 なのに errno が 0 のときは、成功に見えないよう、`EIO` にする

### 進捗パネル（`ProgressState` + `ProgressOverlay`）

時間のかかるコピー・移動の進捗を、ウィンドウの右上に、半透明のパネルで見せる（1 操作 = 1 枚。縦に積む）。ユーザー向けの仕様は README の「ファイル操作の進捗（右上のパネル）」。ここには、設計の決定と罠を書く。以前は、実行中は何も見えず、終わると「完了しました」のダイアログが出て、閉じるまでキー操作を奪っていた。

- **流れ**：裏スレッドが `Job` の進捗を更新（`BeginItem`）→ 毎ティック `Application::Update()` が `file_operations_.Running()`（`FileOperationStatus` の列。写し）を `View::UpdateProgress(now, running)` へ渡す → `ProgressState`（`Update(now, running)`）が、パネルに出す内容の列（`Panels(now)` = `ProgressPanel`: 題・割合・名前・透明度）を決める → `ProgressOverlay::Update(panels)` が描く。完了は、`FileOperationManager::Update()` のコールバック（`OnFileOperationCompleted`）が `View::FinishProgress(id, success, now)` で伝える。`UpdateProgress` は `Update()` の中で、`file_operations_.Update()` の後（`UpdateQuickLook` の隣）に呼ぶ
- **3つに分けた**：`ProgressState`（時刻を引数で受け取る純ロジック。AppKit なし）、`ProgressOverlay`（AppKit。渡された内容を描くだけ。pimpl）、`FileOperationManager`（進捗の写しを作るだけ）。判断（いつ出す・どう消す・何と書く）を画面から切り離して、**時刻を注入して、実時間を待たずに、境界（0.3 秒ちょうど・フェード・期限）を決定的に試す**ため。実時間のテストは、流れが通ることを見るだけにできる
- **`ProgressState` の規則**：(1) **開始から 0.3 秒（`kProgressShowDelay`）たつまで出さない**。透明度は、`(経過 - 0.3 秒) / 0.15 秒`（`kProgressFadeIn`）を 0〜1 に丸めた値で、0 以下のパネルは出さない（時刻が開始より前へ戻っても、何も出ない）。(2) **完了（成功）**は、0.3 秒以上たっていれば `finished_at` を記録して、1.0 秒（`kProgressDoneHold`）見せて、0.4 秒（`kProgressFadeOut`）で消す。**失敗**と、**出す前に終わった操作**は、その場で捨てる（失敗はダイアログで知らせる）。(3) **実行中でも、完了の通知を受けたのでもない**（通知なしに居なくなった）ものは、次の `Update` で捨てる。完了の通知を受けた後の、古い進捗の写しで、「完了」の表示を壊さない。(4) **不定のバーの位置（`pulse`）は、周期 1.2 秒を 24 段に量子化**する（整数のミリ秒で計算。同じ内容なら AppKit に触らないため。0.05 秒のティックで、毎回描き直さない）。(5) **割合**：準備中は不定、バイト数が分かればバイト、項目が 2 つ以上なら項目の数、それ以外は不定。**「n/N」の n は、終えた数 + 1（N が上限）、% は切り捨てで 99 が上限**（100 は完了のときだけ。処理が終わる直前に 100% と出して、続きがあるように見えるのを避ける）。(6) 名前は `RepairUtf8` に通す（UTF-8 として不正だと、NSString にできず、ラベルの作成が例外になる）
- **`Running()` は、終わったが、まだ `Update()` に拾われていない操作も含む**：`Application::Update()` の中で、`file_operations_.Update()` の後、`UpdateProgress` の前に、数 ms かかる処理（自動リロードなど）が挟まる。その間に裏スレッドが終わると、除いていれば、「実行中の一覧から、完了の通知なしに居なくなった」とみなされ、パネルが捨てられて、「完了」が出ない（一覧には、次のティックの `Update()` で完了が届く）。含めておけば、そのティックでは実行中のまま、次のティックで、完了の通知（`FinishProgress`）が先に届き、「完了」になる
- **`std::thread` は `Job` の外（`Entry`）に持つ**：`Job` は `shared_ptr` で、裏スレッドとメイン側が共有する（進捗と結果は mutex の下でだけ触る）。`Job` のメンバーにすると、最後の `shared_ptr` を裏スレッド自身が手放したとき、`join` されていない `std::thread` を、そのスレッドの中で破棄することになり、`std::terminate` する。デストラクタは `detach`（アプリの終了で、走っているスレッドを待たない。従来どおり）。**`Update()` は 2 段**：(1) 終わった操作の結果を、ロックの下で取り出し（`Job::TakeResult`）、`join` して `jobs_` から外す → (2) **その後で**コールバックを呼ぶ。コールバックの中から `Start()` / `Update()` / `Running()` を呼んでも壊れない（`jobs_` を回しながらコールバックを呼ぶと、`push_back` で無効になる）。`Job` は、メインスレッドで、スレッドを起こす前に作る（コンストラクタが `id`・`type`・`started_at`（以降、変わらない）・`total_items`・`Phase::Preparing` を決める。最初の `Running()` で、0 件に見えない）
- **配置と構造**（`ProgressOverlay.mm`）：全面の素通しのホスト（`_MiataProgressHostView`）の子に、パネル 1 枚ごとの自前描画のビュー（`_MiataProgressPanelView`）。`View` のコンストラクタが、`contentView` の、**ブラウザの上**に足す（Quick Look の覆いは、ブラウザの中なので、パネルの奥になる。ダイアログは、開くたびに `contentView` の末尾に足されるので、いつでもパネルの手前）。右端・上端から 12pt、幅 340pt（フォントが 20pt より大きいときは、その比で広げる。窓の幅 - 24pt で頭打ち。0 未満にならない）、パネルの間 8pt。高さはフォントで決まる（`PanelHeight()`。配置とテストが共有する）。**配置は明示計算**（ホストの `setFrameSize:` から `layoutPanels`）：flipped のビューでは、autoresizing の上下のマージンの意味が反転する癖があるので使わない（ホスト自身は、窓への追従に autoresizing の幅・高さを使う）
- **素通し**：ホストもパネルも `hitTest:` が `nil`。`acceptsFirstResponder` は既定の NO のまま（キー入力が `MiataRootView` に届き続ける）。パネルの位置のクリック・ドラッグ・スクロールは、下の一覧に届く（`_MiataQuickLookShield` の逆: あちらは、`QLPreviewView` にクリックを渡さないよう、自分が受ける）。**`isOpaque` は NO のまま**：layer-backed のホストが YES だと、実機の合成で、全面が不透明になる（ヘッドレスの描画では再現しない。構造として、`isOpaque` が NO であることだけを検査している）
- **描き方の罠**：(1) **半透明の塗りは `NSBezierPath` の `fill`（SourceOver）**：`NSRectFill` は Copy 合成で、下を置き換えて、透けない（パネルの背景とバーの塗り。バーの溝の上の塗りは、`NSRectFillUsingOperation(…, SourceOver)`）。(2) **全体の透明度（フェード）は、描画時に `CGContextSetAlpha`**：背景・枠・文字・バーのすべてに掛かる。(3) **`dirtyRect` に `NSRectClip` するだけ（自分の範囲との交わりは、取らない）**：macOS 14 以降、親をまるごと描くと、子の範囲を超えた `dirtyRect` が渡される。ここは、描くものがすべて自分の範囲（`bounds`）から計算した図形・文字で、その中に収まるので、クリップだけで、範囲の外には描かれない。一部だけが渡されたときも、その部分にだけ描く。空や、範囲と重ならない `dirtyRect` なら、何も描かれない（テスト `dirty_clip`）。「ファイル名の検索」の節の罠（`dirtyRect` をそのまま塗らない = `NSIntersectionRect` を取る）は、`QueryBar`・`_MiataQuickLookShield` が、`dirtyRect` そのものを塗るから要る。ここは塗らない。(4) **色は設定のものだけ**（OS の色を使わない）：背景は `Config::Background()` の RGB に、透過度 0.85（`kBackgroundAlpha`）、文字と枠は `normal_text`、バーは `directory`（溝は alpha 0.25）。Light / Dark で見た目は同じ（画素で比べた）。(5) **`wantsLayer = YES`**：パネルの更新が、下の一覧の描き直しを起こさず、一覧のスクロール（`copiesOnScroll`）が、パネルの残像を残さないため。**ヘッドレスでは、効果を確かめられない**（有無で画素が変わらない）ので、`YES` であることだけを検査している（実機で確認が要る）
- **更新は、変わったパネルだけ**：`ProgressOverlay::Update` は、前回と同じ内容なら、AppKit に何もしない（`setNeedsDisplay:` / `setFrame:` / `setHidden:` が 0 回。テストが数える）。変わったパネルだけ `needsDisplay`。枚数が変わったときだけ並べ直し、位置が同じパネルの `frame` は触らない
- **アクセシビリティ**：パネルは、プログレスバーとして読まれる（`NSAccessibilityProgressIndicatorRole`。ラベルは題 + 名前、値は割合で、不定なら値なし）。VoiceOver の読み上げは未確認
- **成功のダイアログを出さない**：以前の `OnFileOperationCompleted` は、成功のとき `ConfirmDialog`（「完了しました」）を出していて、出ている間はキー操作（Normal のキーバインド）を奪った。パネルが「完了」を見せるので削除した。**0.3 秒より早く終わった操作は、何も出ない**：一覧の再スキャン（`ReloadDirectory`）が、完了の合図になる。テストが完了を待つ合図は、以前は「ダイアログが開くこと」だった（`WaitForCompletion`）が、`jobs_` が空になることに変えた（`WaitForOperation`。あわせて、ダイアログが開いていないことも確かめる）
- **タイマーの癖（未確認）**：更新は `pl_start_timer` の `NSTimer`（default モードだけ）なので、メニューの表示中や、ウィンドウのリサイズ中など、イベントを追跡している間は、更新が止まるはず（パネルが止まって見える。コピー自体は、裏スレッドで進む）。自動リロードや Quick Look の追従も、同じ
- **バイト単位の進捗**（`FileOperationProgress::total_bytes` / `done_bytes`。割合の選び方は上の `ProgressState` の規則（5）で、バイトがあればバイト）：
  - **事前の走査**（`Run` の先頭。`MeasureCopyBytes`）：コピーするものの、普通のファイルの `st_size` の合計（再帰。リンクは、たどらず 0。FIFO・ソケット・デバイスも 0。読めないフォルダは 0 で、コピーの失敗で知らせる）。**走査の間は `Phase::Preparing`**（`Start` が、スレッドを起こす前に立てる。題は「準備中」、バーは不定）、終わると `Job::SetTotals` が合計を入れて `Running` にする。20k ファイルで 0.06 秒（実測）。百万ファイルや、遅いボリュームでは、長い「準備中」になりうる
  - **移動は、同じボリュームなら数えない**（`SameVolume`: `lstat(元).st_dev == stat(先のフォルダ).st_dev`。`rename` で終わる=バイトを動かさない）。別のボリュームの移動は数える（コピーして消す）。同じボリュームと見たのに、`rename` が `EXDEV` で、コピーに回る場合（ファームリンクなどを想定。再現できていない）は、合計に入っていないバイトが `done_bytes` に足される：割合は `[0, 1]` に丸められ、題の % は 99 で止まる（`ProgressFraction` / `ProgressTitleText`）
  - **数え方**（`CopyEntry` のファイルとリンクの枝）：`CopySink`（`file_started` / `bytes_done`。`Run` が `Job` へ書く関数を渡す）。`pl_copy_file` の進捗のコールバック（`on_progress`）が、**このファイルの累計**で来るので、足したバイト数 `counted` との差を `bytes_done` に出す。**終えたとき（コピー成功・スキップ）に、`st_size - counted` を足す**：クローンはコールバックが来ない（0 から、ここで全部足される）。**普通にコピーしたファイルでは、最後のコールバックが、ファイルの大きさそのものを報告する**（実測: 12 MiB + 777 バイトで、最後の 3 回が `11534336 / 12582912 / 12583689`）ので、そのときの差は 0 で、何も足さない。足すのは、クローン・スキップ（`counted` が 0）と、コピーの途中で元が縮んだときだけ（`counted` が 0 でも大きさでもない。決定的には作れない=変異 `fo5_final_add_full` は、同値で生き残る）。リンクは足さない（走査で 0 だったので）。**失敗したファイルは足さない**（失敗の操作は、割合が 100% に届かず、パネルはその場で消える）。スキップ（`OnConflict::Skip` で、先に同名がある）したファイルも、終えたものとして足す（最後まで進む）。移動のトップレベルのスキップ（`MoveEntry` の、先に同名があって `overwrite` でない枝）も、`item_bytes[index]`（同じボリュームなら 0）を足す
  - **`current_name` は、いま写しているファイルの名前（葉）**：`BeginItem` が、項目の名前（トップレベル）を入れ、`file_started` が、ファイル・リンクを始めるたびに、その名前に変える（フォルダの名前は出さない）。移動の `rename` は、項目の名前のまま。ファイル名は、バイト列のまま（UTF-8 として不正でも。画面に出す前に、`ProgressState` が `RepairUtf8` に通す）
  - **コストと排他**：`SetCurrentName` はファイルごと、`AddBytes` はコールバック（1 MiB ごと）とファイルの終わりごとに、`Job` の mutex を取る（5000 ファイルのコピーは、0.58 秒 → 0.6 秒で、差は測れない）。メインスレッドは `Running()` の写しだけを読む
  - **`pl_copy_file` の `on_progress`**（`platform.h` / `osx.mm`）：`COPYFILE_STATE_STATUS_CB` と `STATUS_CTX` を、`on_progress` が空でないときだけ付ける。`what == COPYFILE_COPY_DATA && stage == COPYFILE_PROGRESS` のときに、`COPYFILE_STATE_COPIED`（このファイルの累計。実測）を渡す。**別のボリューム（クローンできない）で、1 MiB ほどごとに来る。クローン・リンク・空のファイルでは来ない**（実測）。戻り値は `COPYFILE_CONTINUE`。**ただし、エラー（`stage == COPYFILE_ERR`）では `COPYFILE_QUIT` を返す**：CONTINUE を返すと、man page のとおり、「同じデータの書き込みをやり直す」ので、容量が足りない・書き込み中に先が外れた、のような書き込みの失敗で、**終わらなくなる**（実測 2026-10-07: 12 MiB を 3 MiB のディスクイメージへ。ENOSPC のまま、再試行が 20 万回続いた。ワーカーが止まらず、パネルは固まる）。QUIT なら、コールバックが無いときと同じく、ENOSPC（errno はそのまま）ですぐ失敗する。コードレビューで見つかった。テスト `pl_enospc`（アラームつき）。**中止を足すときは、ここで `COPYFILE_QUIT` を返す**（実測: 進捗の途中で QUIT すると、`-1` / `ECANCELED` で、作りかけの先は消える）
- **まだ無いもの**：中止（`FileOperationManager` に、止める手段が無い。パネルを `hitTest:` で素通しにしているので、ボタンも置けない。作るときは、`Job` に中止の旗、`copyfile(3)` の `COPYFILE_QUIT`、パネルの「中止」の状態を足す）。速度・残り時間
