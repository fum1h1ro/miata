# フォルダの履歴・ペインの状態とウィンドウ位置の保存 — テスト・実測・未確認の記録

> 自動では読み込まれない。テストを書く・直す・検証するとき、実機で確かめることを探すときに読む。
> 設計の決定と罠は `.claude/rules/history-panes.md`。

## フォルダの履歴（ヒストリ）

- **テスト**（リポジトリ外のスクラッチ）：`PathHistory` 単体（別実装との答え合わせ。ランダム操作10万手 × 上限5種）、`FileListModel` の記録点（実ディレクトリ。失敗・`Reload`・`JumpTo`・通知の順序。1つの履歴を2つのモデルで共有する場合と、履歴を渡さない場合）、`pl_*` の往復（想定外の型・不正な UTF-8・プロセスをまたぐ・保存の直後の SIGKILL）、`BrowserModel` の復元と保存（`-[NSUserDefaults setObject:forKey:]` を `class_replaceMethod` で数える）、**実物の `Application::Initialize()` を模擬の `.app` から**（`XDG_CONFIG_HOME` の `init.lua` と、事前に NSUserDefaults に仕込んだ履歴で、シナリオごとにプロセスを分ける）、キー入力 → Lua → コマンド → ダイアログ → 移動（`Application::KeyDown(kVK_ANSI_H, pl_modifier::Shift)`）。**罠**：(1) `dialog_filter_list` は、ダイアログが開く間に2回 `yield` する。キーを押した直後にダイアログを閉じると、コルーチンが待ちに入る前なので、閉じた直後のティックの罠（上記）を再現できない。キーを押して数ティック回し、コルーチンが待ちに入ってから `HandleConfirm()` する。(2) `FileListView::SetCursor` の添字は、画面の並び（ソート後）の添字で、モデルの並び（走査順）ではない。(3) `Lua()` のようなヘルパーが `tostring(f())` で包むと、戻り値の無い関数が「引数が無い」エラーになる。(4) ダイアログの描画（先頭省略）は、実物の `pl_create_main_window` に出して PNG にして見る（`window.appearance` を後から切り替えても、パネルの背景は作成時に解決済みの色のまま。Dark の確認は、最初から Dark で作る）。変異（段落スタイルを外す）で PNG が変わることも確かめた。(5) 一覧のスクロール位置は、`FileListView::NativeView()` の下の `NSScrollView`（`documentView` のクラスが `_MiataFileListNSView`）の `documentVisibleRect.origin.y` で見る。(6) 設定にエラーがある起動は、`XDG_CONFIG_HOME` の `init.lua` に構文エラーを書き、事前に NSUserDefaults に250件を仕込んで確かめる（`Application::Initialize()` はプロセスにつき1回なので、シナリオごとにプロセスを分ける）。(7) 変異テスト（壊して検出できるかの確認）は、ソースの複製の1か所を `perl -0pi` で書き換え、そのファイルだけコンパイルして、ハーネスの `.o` と差し替えてリンクし直す。「どちらか一方を壊しても他方が止める」冗長な条件（たとえば、権限の失敗でなく、かつ `stat` で無いと確定、の2重の判定）は、変異が生き残る。生き残った理由を調べて、冗長なら条件を1つにし、テストで1つずつ効くようにする
- **未確認（実機）**：`<S-h>` の実際の見た目（先頭省略・選択行）、終了 → 再起動での復元、実際の fzf での絞り込みの並び（入力が空のうちは渡した順=新しい順であることは、`FzfFilter` のコードとハーネスで確認済み）

## ペインの状態の保存（いるフォルダ・ソート・フォーカス）

- **テスト**（リポジトリ外のスクラッチ）：(1) `PaneState` の単体テスト（AppKit なし。ASan + UBSan + libc++ の範囲チェック。入力はちょうどの大きさのヒープ）：`IsPlainAbsolutePath` の個別のケースと、別の書き方の参照実装との総当たり（`/` `.` `a` の長さ 0〜9 の全 29524 通り）と乱数 20 万件、`ToMap` / `FromMap` の往復と、壊れた値、乱数 10 万件。(2) 実物の `Application::Initialize()` を模擬 `.app` から起動する（1 回の起動で 1 シナリオ）：**起動をまたぐ復元は、シナリオを続けて別のプロセスで実行し、連鎖の間では保存先（`defaults` のドメイン）を消さない**（保存 → 復元。保存した直後に SIGKILL する連鎖も）。復元の失敗は、作業ツリー（無い・ファイル・0000・親が 0000・自分を指すリンク（ELOOP）・相対パス・`..`）、末尾の `/`、シンボリックリンク（論理パスのまま）、壊れた型（辞書でなく文字列、値が数値）、不明なソートの名前、一部だけ保存、フォーカスの値、空のフォルダ、履歴を動かさないこと、で確かめる。保存の呼び出しは、`-[NSUserDefaults setObject:forKey:]` を差し替えて数える：起動直後のティックで何も書かない、変えたものだけを 1 回書く、同じ値や再読み込みでは書かない、失敗しても保存してある値が残り、そのペインを動かすと更新される。(3) 実装を 1 か所ずつ壊す変異 41 件（`PaneState` 14 件、アプリ全体 27 件）を、すべて検出した：`PaneState`（NUL・`..`・`.`・空の要素・絶対パス・末尾の `/`・ルート・往復・各項目の検査）、復元と保存の呼び出し、保存の基準（未設定・ディスクの値にする）、フォーカス（復元・基準・保存・左右の取り違え）、ソートとパスの復元、履歴への記録（`View` 側とモデル側）、例外を投げる `JumpTo`、毎回の保存、キーの取り違え、ソート名の変換、Lua の `sort`（引数の順序・不明な基準）、`jump_to` の検査、`pl_load_string_map` の型の検査。各変異は、期待した理由のシナリオで落ちる。**罠**：(0) **変異テストを並列に走らせるときは、保存先（`defaults` のドメイン。模擬 `.app` の実行ファイル名）をバッチごとに分ける**：同じドメインを共有すると、互いの保存状態を消し合って、無関係な変異（`sort` の引数の順序など）まで `fresh` が落ちて「検出」になる（偽の検出。実際に起きた）。履歴や選択リストのテストは、保存状態に依存しないので並列でよい。(a) ハーネスは `_build/debug` のオブジェクトにリンクするので、アプリを直したら `rake build:debug` してから、ハーネスをリンクし直す（古いオブジェクトで通った・落ちたと誤解する）。(b) `fb_*` の仕込みは、`Application::Initialize()` の前に `pl_save_string_map` で行う（仕込みと起動の書き込みは、`Initialize()` の後で `ResetSpy()` して数えない）。(c) `chmod 000` のフォルダは、後始末の前に 755 へ戻す（戻さないと消せない）。**ターミナル以外（`open` 起動）での OS の許可ダイアログは、再現していない**（本物の `~/Documents` などを復元先にしない）
- **未確認（実機）**：保護された場所を復元したときの OS の許可ダイアログと、起動の止まり方、実際の終了 → 再起動での見た目（ウィンドウが出たときに、すでに前回の場所にいること）、ネットワークボリューム

## ウィンドウ位置・サイズの保存

- **テスト**：実物の `pl_create_main_window` を、`makeKeyAndOrderFront:`/`activateIgnoringOtherApps:` を何もしないものに差し替えて(画面に出さず)呼べる。ハーネスの実行ファイル名のドメインに保存されるので、本物のアプリの設定には触れない。起動をまたぐ復元は、プロセスを分けて確かめる。
