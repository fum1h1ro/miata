- **テスト**（リポジトリ外のスクラッチ）：実物の `Application::Initialize()` を模擬 `.app` から起動し（1 回の起動で 1 シナリオ）、Lua のコマンドを呼んで、C++ の側の答え（`list_` など）と突き合わせる。17 シナリオ + 連鎖 1 つ（ソートを変えて保存 → 別プロセスで復元して `current_sort` を読む）：初期状態（実物のホーム）、ペインの指定（省略・nil・"left"・"right"・フォーカスの移動・`current_pane()` の戻り値）、全行のカーソル下（フォルダ・ファイル・フォルダへのリンク・ファイルへのリンク・壊れたリンク）、空のフォルダ（nil。外部の変更の後も）、マークの順序（マークした順ではなく表示順。モデルの並びを名前の降順にして、表示順と確実に違う形にする）、ソートの変更への追従、ディレクトリの移動でマークが消えること、再読み込みで保たれること、エントリの形（項目が 3 つで型が決まっている。返した後に書き換えても影響しない）、引数のエラー（4 つのコマンド × （不明なペイン 6 通り + 型違い 4 通り）。状態は変わらない）、設定の読み込み中の呼び出し（`pcall` で受けて、トランポリンのエラー）、ダイアログ表示中、読むだけであること（状態の写しが同じ、保存の呼び出しが 0 回）、変わった名前 9 個（空白・`'`・`"`・日本語・`$()`・`;`・`\`・改行・NFD。`io.open(path)` で開ける）、UTF-8 として不正な名前（模擬のエントリ）、3000 件を全部マーク（2ms ほど）、`test.lua` の `s`（4 つの基準 × 昇降の 8 通りから、ダイアログが始まる。行の選択で降順が引き継がれる。`d` で切り替える。Esc）、README の例のクォート（変わった名前でも、シェルを通って元のパスに戻る。クォート無しでは壊れることも確かめる）、ドラッグ（`BeginDrag`）が `MarkedEntries` を使うこと。AddressSanitizer でも通る。実装を 1 か所ずつ壊す変異 43 件を、すべて検出した（既定のペインの取り違え・登録の抜け・トランポリンを通らない登録・エントリの項目・`is_dir` の反転・空の一覧・モデルの並び・ソートの 2 値の取り違え・`test.lua` の `s` など）。**罠**：(1) 確定（行・ボタン）は次のランループに逃がされる（`dispatch_async`）ので、ハーネスはキーを送った後、ランループを回してからティックする。(2) モデルの並びと表示順が違う形は、走査順（ファイルシステム依存）に頼らず、`entries_` を並べ替えて作る。(3) `io.popen` が使えないので、README の例のクォートの検査は、`os.execute` でファイルに書かせて読む

## ファイルを開く（`open` / `open_with` / `reveal` / `copy_path` / `set_clipboard`）

- **テスト**（リポジトリ外のスクラッチ）：実物の `Application::Initialize()` を模擬 `.app` から起動し（1 回の起動で 1 シナリオ）、外に出る呼び出しを**すべて差し替える**：`-[NSWorkspace openURL:configuration:completionHandler:]` / `openURLs:withApplicationAtURL:…` / `activateFileViewerSelectingURLs:` は記録だけ（完了ハンドラは別のキューから呼ぶ。失敗も返せる）、`+[NSPasteboard generalPasteboard]` は専用のペーストボードを返す（本物のクリップボードに触れない）。**差し替えが、実際に呼ばれる実体（`object_getClass([NSWorkspace sharedWorkspace])` のメソッド）で効いていることを、シナリオの前に確かめる**（効いていなければ、本物のアプリが起動してしまうので、すぐ終了する）。16 シナリオ：開く（文字列・エントリ・配列・混ぜる・フォルダ・`.app`・存在しないパス・空）、対象の形（正しくないもの 25 通り × 4 コマンド、要素の番号を含むエラー文、余分な引数・項目の無視、エントリは配列より優先、内部の `open_paths` / `paths_of` の直接）、変わった名前 9 個（シェルを通らない=コマンド置換が実行されない）、`open_with`（絶対パス・名前・大文字小文字・`.app`・Bundle ID・奥の場所・空白を含む名前・Finder・見つからない 6 通り・不正な引数）、`pl_find_application` の直接、`reveal`、クリップボード（NUL・不正な UTF-8・空・別の形式の消去・型違い）、非同期の失敗（全部・一部・1 件・`open_with`・成功・権限の案内が出ないこと）、確認（10 件はしない・11 件はする・既定は「いいえ」・Esc・`open_with`・`reveal` と `copy_path` はしない・「はい」の後の失敗・3000 件）、Enter（ファイル・フォルダ・フォルダへのリンク・ファイルへのリンク・壊れたリンク・`.app`・空のフォルダ・ダイアログの Enter）、キー（`o` `<S-o>` `yy`。マークの有無・フォルダ・もう一方のペイン・空・ダイアログ中）、設定の読み込み中の呼び出し（5 コマンド）、状態が変わらない・保存が起きないこと、不正な UTF-8 のパス（模擬のエントリ）、3000 件。AddressSanitizer でも通る。実装を 1 か所ずつ壊す変異 74 件を、すべて検出した（`pl_find_application` の各段・各アプリの場所・失敗の集計・`dispatch_group`・クリップボードの `clearContents` / 修復 / NUL・`paths_of` の各検査・登録の抜け・トランポリンを通らない登録・確認の閾値と既定・`test.lua` の Enter / `o` / `O` / `yy` など）。**罠**：(1) `class_replaceMethod` は、`[NSWorkspace class]` に付けても、`sharedWorkspace` が返す実体のクラスが別だと効かない：差し替えの確認を必ず入れる。(2) クリップボードの検査は、専用のペーストボードで行う（本物を書き換えない）。(3) 変異テストの置換は、同じ式が別の場所にもあると、先に見つかった別の場所を壊して「生き残る」：`pl_normalize_string` にも同じ `initWithBytes:valid.data()…` があった。置換には前後の文脈を入れて、壊した場所を確かめる。(4) perl の置換で `$1[` は配列の添字と解釈されて構文エラーになる：`${1}[` と書く。(5) 変異テストのスクリプトの配列とループは、`zsh` では動かない：`bash` で実行する。(6) 確認のダイアログに答えるには、`YesNoDialog::OnButton(yes_id_ / no_id_)` を呼んで、ティックする。(7) 変異のうち、別の層が同じ検査をしていて「生き残る」ものは、冗長な検査だった（`reveal` の空の検査）：片方を、C++ の側のエラーにして、層ごとに 1 つずつ効くようにした

## まとめてマークする（`mark_all` / `unmark_all` / `invert_marks` / `mark_range` / `mark_search_hits` / `next_mark` / `prev_mark`）

- **テスト**（リポジトリ外のスクラッチ）：実物の `Application::Initialize()` を模擬 `.app` から起動し（1 回の起動で 1 シナリオ）、Lua のコマンドを呼んで、C++ の側の答え（`list_` のマーク、カーソル、検索のヒット）と突き合わせる。36 シナリオ：既定（`mark_all` の 2 回目は `n, 0`）、`kind`（3 通り × 3 コマンド。リンクは、`is_dir` と同じ側）、`unmark_all` の既定、反転（2 回で元に戻る）、`pane`（フォーカスが左右どちらのときも。`current_pane()` の戻り値を渡せる）、範囲（上・下・いちばん近いマーク・隣り合う・カーソルの行がマーク済み・起点が無い 4 通り・端・フォルダを含む・反対側のペイン・降順のソート後）、検索ヒット（入力中・確定後・消した後・取り消しや、語が空の確定で、確定済みの検索へ戻った後・スマートケース・`kind` × `mode` の組み合わせ・並べ替えと再読み込みへの追従・検索はペインごと・フォーカスが右のとき）、`next_mark` / `prev_mark`（ラップ・一周して隣の行に着く・カーソルの行だけがマーク済み・マークが無い・1 行だけ・ペイン・降順のソート後=モデルの並びを昇順にして、表示順と違う形にする・中ほどの行へ動くと画面の中央に出る・見えている行へは画面が動かない・フォーカスの無いペインはスクロールしない）、引数のエラー（51 通り：opts が表でない 11・知らない項目・許さない項目・名前が文字列でない・値が文字列でない・知らない値。エラーは何も変えない。メタテーブルの `__index` を呼ばない）、設定の読み込み中の呼び出し（7 コマンド）、ダイアログの表示中、空のフォルダ、1 行だけのフォルダ、再描画の要求（変わったときだけ。5005 行でも 1〜3 回）、5005 件（0.1〜1.4 ms）、既存の機能との組み合わせ（`toggle_mark` / `reload` / ディレクトリの移動 / `marked_entries` の並び）、実際のキー入力（`bind` したキーを `App().KeyDown` で）、README の例（「例：まとめてマークする」のコードを、README から読み出して、そのまま実行して、書いてあるキーを押す）。AddressSanitizer でも通る。実装を 1 か所ずつ壊す変異 120 件（`FileListView` の `ApplyMarkMode` / `MarkKindMatches` / `MarkRows` / 各操作 / `StepMark` と、そこが頼る `JumpCursorTo` と `Redraw` のフォーカス判定、検索の取り消し・確定でのヒットの作り直し、`Application.cc` の opts の読み取り・値の名前・既定値・結果の積み方・登録）を、全て検出した。**罠**：(1) 変異テストの置換は、似た行が別の場所にもあると、別の場所を壊して「生き残る」：置換には、前後の文脈（関数名や、次の関数の宣言）を入れる。(2) 画面の端の行へ動くテストでは、中央寄せと最小のスクロールの結果が同じになる（中央寄せは、文書の端でクランプされる）。マークが最後の行だけのテストは、`JumpCursorTo` を `SetCursor` に変える変異を見逃した（レビューで指摘）：中ほどの行で確かめる。(3) ハーネスの作業ツリーはシナリオで共有するので、ファイルを足すシナリオは、複製を作って、終わったら消す。(4) 検索のヒットは、`FileListView::BeginSearch()` / `SetSearchQuery()` / `CommitSearch()` を直接呼んで作る（検索バーの入力欄を使わない）。(5) `lua_next` の走査順は決まっていないので、エラーの項目が複数あるテストは書かない。(6) **変異テストの実行中に、ランナー・ハーネス・README（例を読み出すシナリオがある）・`src` を編集しない**：後の変異が「未定義のシナリオ」で落ちて、偽の「検出」になる（一度やってしまい、止めてやり直した）。ランナーが自分の出力ファイルを `rm` しないようにも気をつける
- **未確認（実機）**：マークの色が、実際の画面で更新されること（ヘッドレスでは、再描画の要求までを確かめた）、画面の外のマークへ動くときの見え方（中央に出ることは、スクロール位置で確かめた）、`init.lua` に書いたキーバインドでの操作感（README の例のキーは、ハーネスで押して確かめた）
